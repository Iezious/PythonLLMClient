# Step 004 — llama-swap Responses class: streamed tool rounds, plus llama-swap live tool tests

## Goal

Streamed `chat_with_tools` on `LlamaSwapAPIClient` reads each round's Responses event stream with its own copy of the tool-round parser:

- the receiver gets every round's text and reasoning, with each round's reasoning as its own closed block;
- calls are assembled from tool-call events with dense indices, including the llama.cpp sequence where items finish out of order and no arguments-done event arrives;
- reasoning items are carried to later rounds;
- the call returns the final answer without reasoning.

Live tests run a two-round tool conversation on llama-swap and check the tool path on both protocols.

## Interface intent

- **Tool-round stream parser** (new private method on `LlamaSwapAPIClient`, separate from 003's chat parser): same inputs, outputs and handling as step 002's parser (DEC-004-9), written in this module (DEC-arch-2).
- **`chat_with_tools`** (changed): the streamed path builds each round's body as in step 003 with `stream` true and opens it through `_stream_post` on `/responses` (DEC-003-16). It runs the parser inside the trace session without the trace wrapper (DEC-004-10), then continues the loop as the non-streamed path does.
- **003's chat stream parser**: not changed.

## Definition of done

1. [test] Each streamed round opens one streamed request to `/responses`. Its body equals the non-streamed round body except that `stream` is true (DEC-004-10, DEC-004-14).
2. [test] The receiver gets the text pieces of every round in order. The call returns only the final round's text (US-023.AC-1, US-023.AC-2).
3. [test] The receiver gets reasoning text deltas (and summary deltas) as reasoning.
   - Each round's reasoning arrives as its own block, opened and then closed before that round's text.
   - A round that ends in reasoning followed only by function calls has its block closed before the next round's pieces.
   - The returned answer contains no reasoning and no marker.

   (US-027.AC-1, US-027.AC-2, US-058.AC-5, DEC-004-9)
4. [test] The event sequence observed on llama.cpp runs the tool with the full arguments. The next round re-sends the reasoning item ahead of the call. The sequence is:
   1. created, then in progress;
   2. reasoning item added at position 0, then reasoning deltas;
   3. function-call item added at position 1 with name, call id and empty arguments, then argument deltas;
   4. the function-call item done with its full arguments;
   5. the reasoning item done after the call's deltas;
   6. completed, with no arguments-done event and no `[DONE]`.

   (DEC-004-9, DEC-004-7, US-058.AC-3)
5. [test] An arguments-done event or a function-call output-item-done event carrying full arguments replaces the assembled argument text (DEC-004-9).
6. [test] Two function calls at output positions 1 and 2, behind a reasoning item at position 0, run as two calls in order. Each has its own name and arguments, and their outputs carry their own `call_id` (US-035.AC-4, DEC-arch-10, DEC-004-9).
7. [test] The reasoning items collected from a round's done events are re-sent verbatim on every later round, ahead of that round's calls and ordered by output position. The re-sent input has the same layout as the non-streamed path's for the same round (US-058.AC-3, DEC-004-7).
8. [test] No tool-call name or argument text reaches the receiver (DEC-004-9).
9. [test] A failed, incomplete or error event in any round ends the call with `LLMError` carrying the server's reason. So does a round stream that ends without the completed event, including one with a `[DONE]` sentinel. No tool of that round runs and no later piece is delivered (US-060.AC-2, US-024.AC-2, DEC-004-9).
10. [test] A non-2xx reply on a later streamed round ends with `LLMError` carrying the address and the server's reply, for example a 404 with a JSON error body (US-060.AC-1, DEC-arch-5).
11. [test] A receiver failure ends the call with that same exception, and no later piece is delivered. An async receiver is awaited (US-022.AC-1, US-022.AC-2, DEC-000-23).
12. [test] With a requested format, the final round's text pieces join to the returned structured answer (US-037.AC-4).
13. [test] A streamed tool call without a receiver returns the same answer as with one. With tracing enabled, the receiver gets the same pieces and the call returns the same answer as without tracing (US-023.AC-2, US-050.AC-4, DEC-004-10).
14. [manual/live] 003's streamed-chat tests (`tests/test_llamaswap_responses_stream.py`) still pass unchanged (DEC-004-9).
15. [test] (live) On llama-swap Responses with `LLAMA_SWAP_THINKING_MODEL` and thinking on, a two-round tool conversation completes both streamed and not. In each case the tool ran, the final answer is non-empty and the return contains no marker. Streamed, the receiver got at least one reasoning block, and all its reasoning blocks are well-formed (US-058.AC-2, US-058.AC-5, US-027.AC-1, DEC-004-13).
16. [test] (live) On llama-swap with `LLAMA_SWAP_MODEL`, built through the factory on both protocols, a tool conversation gives the same kind of result streamed and not: the tool ran and the final answer is non-empty text. On the streamed run, the returned answer is contained in what the receiver got (US-057.AC-1, US-023.AC-1, US-023.AC-2, DEC-004-13).
17. [test] (live) On llama-swap Responses, a tool conversation with a requested JSON-object format returns a final answer that parses as JSON (US-037.AC-1, DEC-004-13).

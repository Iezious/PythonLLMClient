# Step 002 — OpenAI Responses class: streamed tool rounds, plus OpenAI live tool tests

## Goal

Streamed `chat_with_tools` on `OpenAIAPIClient` reads each round's Responses event stream. The receiver gets every round's text and that round's reasoning as its own closed block. Calls are assembled from tool-call events with dense indices, reasoning items are carried to later rounds, and the call returns the final answer without reasoning. Live tests run a two-round tool conversation on an OpenAI reasoning model and check the tool path on both protocols.

## Interface intent

- **Tool-round stream parser** (new private method on `OpenAIAPIClient`, separate from 003's chat parser):
  - Inputs: an open streamed response and the optional receiver.
  - Outputs: the round text without reasoning, the round's tool calls (dense, in order of first appearance), and the round's reasoning carry items (in output-position order).
  - Reads payloads only through `_iter_sse_data`. Events, markers, completion and failures follow DEC-004-9. It is this module's own copy (DEC-arch-2).
- **`chat_with_tools`** (changed): the streamed path builds each round's body as in step 001 with `stream` true. It opens the body through `_stream_post` on `/responses` (DEC-003-16), runs the parser inside the trace session without the trace wrapper (DEC-004-10), and then continues the loop exactly as the non-streamed path does (DEC-004-6, DEC-004-7, DEC-004-11).
- **003's chat stream parser**: not changed.

## Definition of done

1. [test] Each streamed round opens one streamed request to `/responses`. Its body equals the non-streamed round body except that `stream` is true (DEC-004-10, DEC-004-14).
2. [test] The receiver gets the text pieces of every round in order. The call returns only the final round's text (US-023.AC-1, US-023.AC-2).
3. [test] The receiver gets reasoning text and reasoning summary deltas as reasoning.
   - Each round's reasoning arrives as its own block: opening marker first, closed before that round's text. A round that ends in reasoning followed only by function calls has its block closed before the next round's pieces.
   - The returned answer contains no reasoning and no marker.

   (US-027.AC-1, US-027.AC-2, US-058.AC-5, DEC-004-9)
4. [test] A call is assembled from its output-item-added event and its argument deltas, and the tool runs with the assembled arguments.
   - When an arguments-done event or a function-call output-item-done event carries full arguments, those replace the assembled text.
   - The next round's input holds that call with its `call_id`, name and arguments.

   (DEC-004-9, DEC-004-6)
5. [test] Two function calls in one round, at output positions 1 and 2 behind a reasoning item at position 0, run as two calls in order. Each has its own name and arguments. Their outputs carry their own `call_id` (US-035.AC-4, DEC-arch-10, DEC-004-9).
6. [test] The reasoning items from the round's reasoning output-item-done events are re-sent on the next round, verbatim and ahead of that round's function calls.
   - They are ordered by output position even when a reasoning item finished after the call's deltas.
   - The re-sent input has the same layout as the non-streamed path's for the same round.

   (US-058.AC-3, DEC-004-7, DEC-004-9)
7. [test] No tool-call name or argument text reaches the receiver (DEC-004-9).
8. [test] A failed, incomplete or error event in any round ends the call with `LLMError` carrying the server's reason. So does a round stream that ends without the completed event, including one with a `[DONE]` sentinel. No tool of that round runs and no later piece is delivered (US-060.AC-2, US-024.AC-2, DEC-004-9).
9. [test] A non-2xx reply on a later streamed round ends with `LLMError` carrying the address and the server's reply, and not the credential (US-060.AC-1, US-060.AC-4, DEC-arch-5).
10. [test] A receiver failure ends the call with that same exception, and no later piece is delivered. An async receiver is awaited (US-022.AC-1, US-022.AC-2, DEC-000-23).
11. [test] With a requested format, the final round's text pieces join to the returned structured answer (US-037.AC-4).
12. [test] A streamed tool call without a receiver returns the same answer as with one. With tracing enabled, the receiver gets the same pieces and the call returns the same answer as without tracing (US-023.AC-2, US-050.AC-4, DEC-004-10).
13. [manual/live] 003's streamed-chat tests (`tests/test_openai_responses_stream.py`) still pass unchanged: the chat parser's return still equals what the receiver got (DEC-004-9).
14. [test] (live) On OpenAI Responses with `OPENAI_REASONING_MODEL`, a two-round tool conversation completes, both streamed and not. In each case the tool ran, the final answer is non-empty, and the return contains no marker. Streamed, the receiver's reasoning blocks are well-formed. Skipped without a key (US-058.AC-1, US-058.AC-2, US-058.AC-5, DEC-004-2, DEC-004-13).
15. [test] (live) On OpenAI with `OPENAI_MODEL`, built through the factory on both protocols, a tool conversation gives the same kind of result streamed and not: the tool ran and the final answer is non-empty text. On the streamed run, the returned answer is contained in what the receiver got (US-057.AC-1, US-023.AC-1, US-023.AC-2, DEC-004-13).
16. [test] (live) On OpenAI Responses, a tool conversation with a requested JSON-object format returns a final answer that parses as JSON (US-037.AC-1, DEC-004-13).

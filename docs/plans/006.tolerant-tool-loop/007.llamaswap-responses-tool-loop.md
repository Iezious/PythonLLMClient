## Interface intent

- **`LlamaSwapAPIClient.chat_with_tools`** (changed) — gains keyword-only `tool_errors` (literal `"raise"` / `"result"`, default `"result"`) and `on_tool_event` (optional callable receiving one `ToolEvent`, plain or returning an awaitable). Runs the per-call procedure of `context.md` for every requested call, streamed and non-streamed rounds alike; everything else in the loop is unchanged.
- **One-call execution helper** (new private method of `LlamaSwapAPIClient`, name chosen by the skeleton) — same responsibility as in step 006, as this class's own copy; no import from `llm/openai.py`.
- **Existing helpers** (`_offered_tool_name`, `_read_tool_arguments`, `_tool_result_text` in this module) — their `LLMError` raises carry `kind="tool"`; messages unchanged.
- **Argument-name check** — per DEC-arch-16; first undeclared name in the model's order.
- **Docstring** of `chat_with_tools` — documents `tool_errors` / `on_tool_event`; if it describes each round's reasoning as "its own closed `<think>` block", corrected to the incremental marker behaviour (code unchanged).

## Definition of done

Unless stated, each item holds without passing `tool_errors` (the default) and is checked on a non-streamed conversation; "the model is told X" means the next round's request carries a function-call output for that call whose output is exactly X (texts: DEC-arch-14).

- DoD-1 [test] A requested tool that was not offered (and an empty tool name) runs no callable; the model is told `Tool '<n>' is not available.`; the next round runs and the call returns its answer. Cites US-064.AC-1, US-064.AC-12, US-064.AC-13, US-064.AC-20.
- DoD-2 [test] Arguments that are not valid JSON, and JSON that is not an object, run no callable; the model is told `Invalid arguments for tool '<n>'.`; the conversation continues. Cites US-064.AC-2, US-064.AC-14, US-064.AC-15.
- DoD-3 [test] An argument name the callable does not declare runs no callable; the model is told `Tool '<n>' has no argument '<arg>'.` naming the first undeclared name in the order sent; the conversation continues. Cites US-064.AC-3, US-064.AC-16.
- DoD-4 [test] A tool (sync, and async) that raises an ordinary exception: the model is told `Tool '<n>' failed.`, and the text sent contains nothing of the exception's message; the conversation continues. Cites US-064.AC-4, US-064.AC-17.
- DoD-5 [test] A tool result that cannot be turned into text: the model is told `Tool '<n>' failed.`; the conversation continues. Cites US-064.AC-5, US-064.AC-18.
- DoD-6 [test] Three calls in one round where the middle one fails: the first and third tools run, in the order requested, and every call gets its own function-call output in that order. Cites US-064.AC-6.
- DoD-7 [test] Streamed and non-streamed: round 1 requests an unoffered tool, round 2 sends arguments that are not an object, round 3 passes an unknown argument, round 4 answers → the call returns round 4's answer without an error. Cites US-064.AC-7.
- DoD-8 [test] A model that requests a failing call in every round ends with the round-limit `RuntimeError` stating the limit and its value. Cites US-064.AC-8.
- DoD-9 [test] A tool that raises cancellation: the cancellation propagates out of the call, no further round is requested and no function-call output is sent for it; also with an observer, no `error` event is sent for it. Cites US-064.AC-9, US-064.AC-19.
- DoD-10 [test] With `tool_errors="raise"`, each failure kind ends the call as before: `not_offered`, `bad_arguments`, `unserialisable_result` → `LLMError` with today's text and `kind == "tool"`; `unknown_argument` → `ValueError`; `tool_raised` → `RuntimeError` naming the tool, chained from the tool's exception; no further round is requested. The class's existing tests that expect these raises pass `tool_errors="raise"` and keep their assertions. Cites US-064.AC-10, US-067.AC-2.
- DoD-11 [test] A callable declaring `**kwargs` runs with exactly the arguments the model sent, in both modes; a callable whose signature cannot be read is called without the name check. Cites US-066.AC-1.
- DoD-12 [test] With an observer, before a tool runs the observer receives a `start` event with the requested name, the call's Responses call id and the arguments exactly as sent (string verbatim; `output` and `error_kind` none). Cites US-065.AC-1.
- DoD-13 [test] After a successful tool, the observer receives a `result` event whose `output` equals the output text sent to the model. Cites US-065.AC-2.
- DoD-14 [test] For each of the five failure kinds, the observer receives `start` then an `error` event with the name, call id, arguments as sent and the matching `error_kind` — including `not_offered` and `bad_arguments`, where no tool runs. Cites US-065.AC-3.
- DoD-15 [test] With several calls, events arrive in call order (`start`, then `result` / `error`, per call); a coroutine observer's work for `start` has finished before the tool is called. Cites US-065.AC-4, US-065.AC-5.
- DoD-16 [test] With `tool_errors="raise"` and an observer, the failing call's `error` event is received before the call's exception reaches the caller. Cites US-065.AC-6.
- DoD-17 [test] With `tool_errors="raise"`, an observer that raises (on `start`, and on `result`) ends the call with that same exception unchanged; when it raised on `start` the tool did not run. Cites US-065.AC-7.
- DoD-18 [test] Tolerant: an observer that raises on `start` → the tool does not run; the model is told `Tool '<n>' failed.`; the conversation continues; the observer receives no further event for that call, while later calls still get their events. Cites US-065.AC-8, US-065.AC-11, US-065.AC-12.
- DoD-19 [test] Tolerant: an observer that raises on `result` → the model is told `Tool '<n>' failed.` instead of the tool's result (DEC-006-8); no further event for that call. Cites US-065.AC-11, US-065.AC-12.
- DoD-20 [test] Tolerant: each observer failure emits exactly one `LLMToolObserverWarning`, and the call still returns its answer. Cites US-065.AC-9.
- DoD-21 [test] With tracing enabled: a tolerant tool failure writes `TOOL RESULT` with the model-facing text followed by `TOOL ERROR` with the failure kind name; a tolerant observer failure writes `TOOL ERROR` with the observer-failure note (DEC-006-7). Cites US-065.AC-13.
- DoD-22 [test] The observer `arguments` field is empty text when the call carried no arguments, and JSON text when the arguments arrived as a mapping (DEC-006-4). Cites US-065.AC-1.
- DoD-23 [manual/live] The `chat_with_tools` docstring documents `tool_errors` / `on_tool_event` and describes reasoning markers as incremental per round where it mentions them.
- DoD-24 [manual/live] `llm/llama_swap.py` imports nothing tool-loop-related from `llm/openai.py` (independent copy, DEC-arch-15); the step-002 typing test and the rest of the existing unit suite stay green.

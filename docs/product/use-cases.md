# Use cases

### UC-001 — Build a client for a registry entry
- **Feature:** FEAT-001 · **Actors:** ACT-001, ACT-002
- **Preconditions:** the developer knows the backend kind, server address, credential and model (from the app's registry).
- **Main flow:**
  1. The developer asks the library for a client, giving the backend kind, the server address and the model; the credential when the backend takes one (required for OpenAI, optional for llama-swap); optionally a time limit for calls and default generation settings.
  2. The library returns a client bound to that backend, address and model, without contacting the server.
  3. The developer opens a usage scope on the client, makes calls (FEAT-002..FEAT-009), and closes it; the library releases its connection to the server.
  4. Every call goes to the model given at creation.
- **Alternate flows:**
  - A1 Reuse: after the usage scope closes, the same client can be used again.
  - A2 No usage scope: calls work; the connection is opened on first call (its release is the FEAT-001 gap).
  - A3 OpenAI: the app provides the credential when building the client.
  - A4 llama-swap with or without a credential; a given credential reaches the server on every request.
- **Exception flows:**
  - E1 Unknown backend kind: refused at creation; the error names the kind.
  - E2 OpenAI with no credential provided: refused when the client is built; the message tells the developer to provide one and shows no credential.
  - E3 Wrong address, unreachable server or unknown model: not detected at creation; surfaces as an error on the first call.
- **Postconditions:** the client is bound to one backend, address and model; its connection is released when the usage scope closes.
- **Source:**

  - A3, E2 (credential from the app): `[confirmed: user]` interview "I-01 — wave-1 checkpoint (CORRECTION)" (2026-11-07)
  - A4 (llama-swap optional credential): `[confirmed: user]` interview "I-01 — wave-1 checkpoint (CORRECTION)" (2026-11-07)

  2. The library sends it to the client's model, the instruction first.
  3. The developer receives the reply text.
  4. The developer's conversation is unchanged.
- **Alternate flows:**

  - E4 Reply with no content: should be empty text (defect, FEAT-002 gap).
  - E5 Empty conversation: should be refused before the server is contacted (FEAT-002 gap).
  - E6 Deprecated Ollama: streaming is refused before anything is sent.
- **Postconditions:** the developer holds the reply text; the conversation is as it was.

### UC-004 — Tune generation with layered settings

- **Main flow:**

### UC-005 — Stream a reply
- **Feature:** FEAT-004 · **Actors:** ACT-001, ACT-002

- **Main flow:**
  1. The developer asks for a streamed chat or generation with a piece receiver.
  2. Each piece goes to the receiver as produced, in order, one at a time.
  3. The call returns the whole text.
- **Alternate flows:**
  - A1 The receiver is a plain or an awaitable function.
  - A2 No receiver: the whole text is returned at the end (US-008).

  - E4 The receiver fails: the stream stops; the call ends with that failure.
  - E5 Deprecated Ollama: streaming is refused before the server is contacted.
- **Postconditions:** the developer holds the whole text; the receiver got every piece produced before any failure.

### UC-006 — See the model's reasoning
- **Feature:** FEAT-005 · **Actors:** ACT-001, ACT-002

- **Main flow:**

  2. The receiver gets the reasoning first, marked as one reasoning block, then the answer.
  3. The call returns the marked reasoning followed by the answer, as streamed.
- **Alternate flows:**
  - A1 The reply ends while reasoning: the block is closed.
  - A2 Reasoning resumes after answer text: a new block starts.
  - A3 Streamed tool conversation: each round's reasoning is its own closed block; the returned answer has no reasoning; on chat completions, earlier reasoning is not sent back to the model. On Responses, each round's reasoning is sent back to the server within the call (FEAT-014). This holds for reasoning the server reports separately from the answer; reasoning the server writes directly into the answer text is returned and sent back as part of the answer (accepted).
  - A4 A model that does not reason: no blocks appear.
  - A5 Not streaming: the answer only.
  - A6 OpenAI: thinking on asks for the default reasoning effort; an explicit effort wins; the server's reasoning text is not shown. On Responses: OpenAI reasoning summary asked (UC-013 A3).
  - A7 Thinking off: llama-swap tells the server (unverified, gap); OpenAI should ask for the lowest effort (defect). On Responses: thinking off asks for the lowest reasoning (UC-013 A4).
  - A8 Deprecated Ollama: the switch is ignored.
- **Exception flows:**
  - E1 The stream fails during reasoning: the call fails; the block is left open (observed).
  - E2 A piece carries both reasoning and answer text: the answer text is lost (defect, FEAT-005 gap).
- **Postconditions:** the developer holds the streamed text, reasoning included for a plain chat.

### UC-007 — Let the model use the app's tools
- **Feature:** FEAT-007 · **Actors:** ACT-001, ACT-002
- **Preconditions:** a client (UC-001) on any backend.
- **Main flow:**
  1. The developer passes a conversation, tool descriptions and a function per tool.
  2. Every offered tool is checked to have a function before the server is contacted.
  3. The conversation and tools are sent to the model.
  4. The model asks for tools; they run one after another, in the order asked (a function may be plain or awaitable).
  5. Each result goes back to the model as text, then the next round starts.
  6. When the model answers without asking for a tool, that answer is returned.
- **Alternate flows:**
  - A1 The model answers in the first round: no tool runs.
  - A2 A tool is described from a typed data model.
  - A3 A system instruction is sent first.
  - A4 A different round limit for one call.
  - A5 A requested answer format (any JSON, or a given shape) applies to every round; the answer comes back in that shape.
  - A6 Streamed: see UC-005 A3 and UC-006 A3.
  - A7 Deprecated Ollama: a requested shape becomes "any JSON" (observed).
- **Exception flows:**
  - E1 An offered tool has no function: refused before the server is contacted.
  - E2 A tool fails, or the model passes an argument the tool lacks: the call ends with an error naming the tool; tools already run keep their effects; the model is not told.
  - E3 The round limit is reached: error, no partial answer; the last round's tools ran. The error should name the round limit as the reason (defect, FEAT-007 gap).
  - E4 The model requests an unoffered tool, its argument text cannot be read, or a tool result cannot be made into text: today a raw program error (defect, FEAT-007 gap).
  - E5 Streamed tool requests arrive without position numbers or with repeated names: merged into one broken call (defect, FEAT-007 gap).
- **Postconditions:** the developer holds the final answer, or the call ended with an error.
- **Source:**
  - E2 (the call ends, the model is not told), E3 (error reason), E4, E5, A5 (format on every round): `[confirmed: user]` interview "Wave 4 — FEAT-007 tools + stream parsing (batched)" (2026-11-07)

### UC-011 — Inspect an LLM interaction
- **Feature:** FEAT-011 · **Actors:** ACT-001
- **Preconditions:** none.
- **Main flow:**
  1. The developer turns tracing on and names a folder before creating the client.
  2. The app makes any call (chat, generate, JSON-only, tool conversation, embedding).
  3. One new readable record per call is written, grouped by day, filled as the call proceeds, and ending with an end marker.
  4. The record shows the operation, model, time, instruction, conversation, request, each streamed piece of a plain streamed chat, each tool request and result (rounds numbered), and the answer; for embeddings, only how many vectors came back.
- **Alternate flows:**
  - A1 Tracing off, or only one of the two settings given: no record, and the call behaves the same.
  - A2 Settings changed after the client exists: no effect on that client.
  - A3 The app writes its own records through the library's trace facility (supported).
- **Exception flows:**
  - E1 The call fails: the record ends with the error, and the same error reaches the app.
  - E2 The folder cannot be written: today the call fails before anything is sent (defect, FEAT-011 gap: it should go ahead untraced).
  - E3 Calls start at the same instant: one record can overwrite another (defect, FEAT-011 gap).
  - E4 Writing the record fails while an error is being recorded: the call's own error is replaced (defect, FEAT-011 gap).
- **Postconditions:** each traced call has one record; the call's outcome is as without tracing.

### UC-013 — Talk to a server through the chosen chat protocol
- **Feature:** FEAT-014 · **Actors:** ACT-001, ACT-002

  1. The developer builds a client without naming a protocol; it speaks Responses.

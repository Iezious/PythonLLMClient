**Stage:** 002.responses · **Feature:** 003.responses-chat

Planning-time decisions for the Responses protocol on chat, generate and JSON-only answers, the chat-completions class names, the factory's protocol choice and the ignored-setting warning. Plan: `docs/plans/003.responses-chat/`. The design they realize is DEC-arch-1..12 (`arch-responses-protocol.md`); DEC-003-1 and DEC-003-2 settle the two open sub-points of DEC-arch-8 (flipped at finalization, not now). ### DEC-003-1 — Thinking off on Responses asks for effort none; an explicit effort wins
- **Status:** accepted
- **Stage:** 002.responses · **Feature:** 003.responses-chat · **Step:** 002, 004
- **Date:** 2026-11-07 · **Decided by:** user
- **Question:** Which reasoning effort does a Responses request carry when the app turned thinking off (DEC-arch-8, first open sub-point)?
- **Decision:** When `enable_thinking` is set and falsy, both Responses classes (OpenAI and llama-swap) send `reasoning: {"effort": "none"}`. An explicit `reasoning_effort` set by the app always wins and is sent instead (an app on an older model sets e.g. `"minimal"` itself). There is no retry with another value; a server that refuses the value answers non-2xx and the call ends with `LLMError` carrying the server's reason (DEC-000-11). Evidence (live probe, 2026-11-07): gpt-6-luna accepts `none` and `low` and refuses `minimal`; gpt-5-mini accepts `minimal` and refuses `none`; gpt-4o-mini refuses any `reasoning.effort` ("Unsupported parameter") but accepts a request with no reasoning field and with `include: ["reasoning.encrypted_content"]` and `store: false`.
- **Reason:** `none` is the lowest value current reasoning models accept, and the app keeps full control through the explicit effort.
- **Rejected:** A built-in model-id → effort table (goes stale with every model release). Sending nothing when thinking is off (the model reasons at its default, failing US-059.AC-3 and US-025.AC-5).
- **Lands in:** `_merge_options` in `llm/openai.py`, `llm/llama_swap.py`
- **Cites:** docs/architecture/subsystems.md § Options layer; docs/architecture/interfaces.md § Protocol axis; DEC-arch-8; US-059.AC-3; US-025.AC-5

### DEC-003-2 — llama-swap receives thinking on Responses as the reasoning effort, like OpenAI
- **Status:** accepted
- **Stage:** 002.responses · **Feature:** 003.responses-chat · **Step:** 004, 005
- **Date:** 2026-11-07 · **Decided by:** planner (settled by live probe, 2026-11-07)
- **Question:** How do thinking on/off and an explicit effort reach the engine on the llama-swap Responses class (DEC-arch-8, second open sub-point)?
- **Decision:** Exactly as on the OpenAI Responses class, through `reasoning.effort`: thinking on → `"medium"` unless the app gave an effort (the existing default, DEC-000-19); thinking off → `"none"` unless the app gave an effort (DEC-003-1); an explicit effort is always sent (US-025.AC-6). `enable_thinking` and `reasoning_effort` are never sent as top-level fields. llama-swap gets no `reasoning.summary` (DEC-arch-7 is OpenAI only). Evidence (llama-swap at `http://india.loc:9292/v1`, llama.cpp, model `Qwen3.8-27B-Uncensored-FP8.i1-Q5_K_M`): no reasoning field → the model reasons (a `reasoning` output item with `reasoning_text` content, empty `summary`, empty `encrypted_content`); `effort: "none"` → no reasoning item; `effort: "low"` → reasons. The chat-completions llama-swap class keeps DEC-000-19 unchanged.
- **Reason:** The engine honours the protocol's own reasoning setting, so one mapping serves both backends and an explicit effort finally reaches llama-swap.
- **Rejected:** Sending the top-level thinking switch on Responses (not a Responses field; the probe shows the effort setting works).
- **Lands in:** `_merge_options` in `llm/llama_swap.py`
- **Cites:** docs/architecture/interfaces.md § Protocol axis (thinking control row); DEC-arch-7; DEC-arch-8; DEC-000-19; US-025.AC-1, US-025.AC-2, US-025.AC-6

### DEC-003-6 — The warning is emitted at call time, once per setting per client instance
- **Status:** accepted
- **Stage:** 002.responses · **Feature:** 003.responses-chat · **Step:** 002, 004
- **Date:** 2026-11-07 · **Decided by:** planner
- **Question:** When exactly is the ignored-setting warning emitted, and how is "once per setting per client" kept?
- **Decision:** In the Responses classes' settings post-processing, i.e. on every chat-style call (`chat`, `generate`, `chat_json`) after the merge. For each no-counterpart key present in the merged settings (DEC-003-9), if the client has not warned about that key before, it calls `warnings.warn` with category `LLMSettingIgnoredWarning` and a message naming the setting and saying the Responses protocol has no counterpart so it was not sent; then it records the key in a per-instance set created in the constructor. Python's own warning filters still apply on top (an app may silence or escalate the category). A key cleared to `None` or never set is not warned about. Nothing is emitted at construction, nor by `embed_batch`, `list_models` or `get_models`. Tests count emissions with all filters set to "always" so Python's per-location de-duplication does not interfere.
- **Reason:** Settings are merged per call, so only a call knows what was actually dropped; the per-instance record gives the agreed frequency regardless of the app's filter configuration.
- **Rejected:** Warning in the constructor (misses per-call options). Relying on Python's default "once per location" filter (would warn once per process, not per client).
- **Lands in:** `llm/openai.py`, `llm/llama_swap.py` (constructor, `_merge_options`)
- **Cites:** docs/architecture/interfaces.md § Exposed: warnings; DEC-arch-6; US-061.AC-1, US-061.AC-2

### DEC-003-8 — Factory protocol argument: last keyword, None means not passed
- **Status:** accepted
- **Stage:** 002.responses · **Feature:** 003.responses-chat · **Step:** 001
- **Date:** 2026-11-07 · **Decided by:** planner
- **Question:** How does `get_llm_client` tell "no protocol named" from `"responses"`, and in which order are refusals checked?
- **Decision:** `protocol` is appended as the last parameter with default `None`; existing positional calls are unaffected. Order: (1) unknown `server_type` → `ValueError` as today; (2) `server_type == "ollama"` with `protocol` not `None` → `ValueError` saying a protocol choice is not offered on Ollama, whatever the value; (3) for `openai` / `llamaswap`: `None` or `"responses"` → `OpenAIAPIClient` / `LlamaSwapAPIClient`, `"chat_completions"` → `OpenAIChatCompletionsClient` / `LlamaSwapChatCompletionsClient`, anything else → `ValueError` naming the value and the accepted values. Matching is exact (no case folding or trimming, DEC-000-3). The chosen class receives `model`, `base_url`, `timeout`, `bearer_token` and `default_options` exactly as today; the address never influences the choice. Passing `protocol=None` explicitly is the same as not passing it.
- **Reason:** A `None` default is the only way to refuse an explicit protocol on Ollama without a sentinel object, and appending keeps every existing call valid.
- **Rejected:** Default `"responses"` (cannot tell an explicit choice on Ollama). A private sentinel default (no observable gain over `None`).
- **Lands in:** `llm/llm.py` (`get_llm_client`)
- **Cites:** docs/architecture/interfaces.md § Exposed: factory; DEC-arch-4; DEC-000-3; US-056.AC-1, US-056.AC-2, US-056.AC-3, US-056.AC-5

### DEC-003-9 — Responses settings table and wire mapping
- **Status:** accepted
- **Stage:** 002.responses · **Feature:** 003.responses-chat · **Step:** 002, 004
- **Date:** 2026-11-07 · **Decided by:** planner
- **Question:** Which keys do the Responses classes accept, and what does each become on the wire (DEC-arch-8)?
- **Decision:** Both Responses classes accept the same app-facing keys as the chat-completions classes, every table value `None` (no built-in values): `temperature`, `top_p`, `max_tokens`, `presence_penalty`, `frequency_penalty`, `seed`, `stop`, `logit_bias`, `user`, `response_format`, `enable_thinking`, `reasoning_effort`; alias `context_length` → `max_tokens`. The merge is `_merge_options_base` unchanged (DEC-000-5). Post-processing turns the merged settings into wire fields:
  - `temperature`, `top_p`, `user` → sent under the same name (Responses still accepts `user`).
  - `max_tokens` → `max_output_tokens`.
  - `response_format` → `text: {"format": …}` per DEC-003-10.
  - `presence_penalty`, `frequency_penalty`, `seed`, `stop`, `logit_bias` → not sent; warning per DEC-003-6.
  - `enable_thinking` / `reasoning_effort` → a `reasoning` object, never top-level: thinking on → `effort` = the explicit effort, else `"medium"`; OpenAI only adds `summary: "auto"` (DEC-arch-7). Thinking off → `effort` = the explicit effort, else `"none"` (DEC-003-1); no summary. Thinking unset → `{"effort": <explicit>}` when an effort is set (no summary), else no `reasoning` field. "Thinking on" means `enable_thinking` is truthy; an explicit effort alone does not request a summary. llama-swap: DEC-003-2.
  - Values are passed through unvalidated; keys outside the table are dropped silently, without a warning.
- **Reason:** Only the app's settings are sent, translated to the Responses names; keys with no counterpart are visible to the developer through the warning instead of failing the call.
- **Rejected:** Sending `user` as `safety_identifier` (a rename no story asks for; `user` is still accepted). Requesting the summary whenever an effort is set (DEC-arch-7 ties the summary to the thinking switch).
- **Lands in:** supported tables and `_merge_options` in `llm/openai.py`, `llm/llama_swap.py`
- **Cites:** docs/architecture/subsystems.md § Options layer; docs/architecture/data-model.md § Settings; DEC-arch-7; DEC-arch-8; DEC-000-5; DEC-000-19; DEC-001-13; DEC-001-14; US-018.AC-1; US-025.AC-3, US-025.AC-4; US-059.AC-2

### DEC-003-10 — Response format is translated to the Responses text format
- **Status:** accepted
- **Stage:** 002.responses · **Feature:** 003.responses-chat · **Step:** 002, 004
- **Date:** 2026-11-07 · **Decided by:** planner
- **Question:** How is today's `response_format` shape written as the Responses text-format setting, and what does `chat_json` send (DEC-arch-10, minus tools)?
- **Decision:** The translated value is sent as `text: {"format": <format>}`:
  - `{"type": "json_object"}` → `{"type": "json_object"}`.
  - `{"type": "json_schema", "json_schema": {…}}` → `{"type": "json_schema", …}`: the nested mapping's keys (`name`, `schema`, `strict`, `description`, whatever is present) are lifted beside `type`.
  - `{"type": "text"}` → `{"type": "text"}`.
  - Any other value (including a format already in the flat Responses shape) is sent unchanged as the format.
  `chat_json` sends the translated `response_format` setting when the app set one, otherwise `{"type": "json_object"}` (the Responses form of DEC-001-2); its parse check is unchanged (DEC-000-37, DEC-002-7). The same translation applies to `chat` and `generate` when the setting is set.
- **Reason:** App-facing shapes stay the same on both protocols (DEC-arch-10); passing unknown shapes through keeps apps that already use the Responses form working.
- **Rejected:** Refusing unknown shapes (the server is the authority on what it accepts).
- **Lands in:** `llm/openai.py`, `llm/llama_swap.py` (settings post-processing, `chat_json`)
- **Cites:** docs/architecture/data-model.md § Tool definition (response format paragraph); docs/architecture/interfaces.md § Protocol axis (`chat_json` request row); DEC-arch-10; DEC-001-2

### DEC-003-11 — Responses request body: exact keys and input items
- **Status:** accepted
- **Stage:** 002.responses · **Feature:** 003.responses-chat · **Step:** 002, 003, 004, 005
- **Date:** 2026-11-07 (amended 2026-11-08) · **Decided by:** planner (amendment: user)
- **Question:** What exactly does a chat-style Responses request carry?
- **Decision:** `POST /responses` with a JSON body holding exactly: `model`; `input` — the list of input items; `stream` — always present, `true` or `false`; `store: false`; `include: ["reasoning.encrypted_content"]` (DEC-arch-7); plus the wire fields from DEC-003-9. No `instructions` field. Each caller message becomes one item, in order, values as given: a message whose role is `assistant` becomes `{"type": "message", "role": "assistant", "content": <content>}` — exactly those three keys; every other caller message (system, user) becomes `{"role": <role>, "content": <content>}` — only those two keys. A truthy `system` becomes the bare item `{"role": "system", "content": <system>}` at the head of a copy (DEC-arch-3); an empty `system` adds nothing (US-007). `generate` sends `[system item when truthy, {"role": "user", "content": <prompt>}]` (DEC-000-8). `chat_json` sends `stream: false`. The same item rule applies to every operation that builds input items: `chat` (streamed and not) and `chat_json`; `generate` has no assistant turn.
- **Reason:** The short role/content item form is accepted by OpenAI and by llama.cpp's Responses route for system and user items, but llama.cpp refuses an assistant item without `"type": "message"` (400 "Cannot determine type of 'item'"; probe of 2026-11-07, recorded in `docs/plans/004.responses-tools/context.md` § Responses wire vocabulary for tools); the typed assistant item is accepted by both servers. A fixed key set makes the request testable and sends nothing the app did not ask for.
- **Rejected:** Bare role/content items for assistant turns (the original 2026-11-07 decision; llama.cpp cannot determine the item's type and refuses the request). Typed `message` items for system and user turns too (longer, no gain: both servers accept the bare form). Typed content parts (longer, no gain for text-only messages). Copying extra message keys (Responses rejects unknown item fields).
- **Amended:** 2026-11-08, user (via the orchestrator) — assistant items carry `"type": "message"`; system and user items stay bare. Previously every item was bare role/content. Applied to the delivered code as a plan-side correction of feature 003 (`docs/plans/003.responses-chat/status.md` § Notes & Issues).
- **Lands in:** `llm/openai.py`, `llm/llama_swap.py` (payload building in `chat`, `generate`, `chat_json`)
- **Cites:** docs/architecture/interfaces.md § Consumed: backend APIs; docs/architecture/data-model.md § Message; DEC-arch-3; DEC-arch-7; DEC-000-8; DEC-004-4; US-006.AC-2, US-006.AC-3; US-007

### DEC-003-12 — Non-streamed Responses reply: text extraction and failed or incomplete status
- **Status:** accepted — amended by DEC-arch-13 (2026-11-08)
- **Stage:** 002.responses · **Feature:** 003.responses-chat · **Step:** 002, 004
- **Date:** 2026-11-07 · **Decided by:** planner
- **Question:** How is the answer read from a non-streamed Responses reply, and what happens when the reply's status says it failed or is incomplete?
- **Decision:** From the reply mapping's `output` list, every item of type `message` is visited in order and the `text` of each content part of type `output_text` is concatenated with no separator. Reasoning items and other part types (e.g. refusal) are ignored, so no `<think>` text appears off-stream (US-028.AC-1). A missing or non-list `output`, no message item, or a null/missing `text` gives `""` (the Responses form of DEC-001-12). Status: `"failed"` → `LLMError` whose description is the server's reason — `error.message` when the reply's `error` is a mapping with a string message, else the `error` value as JSON text; `"incomplete"` → `LLMError` whose description is `incomplete_details.reason` when present, else the `incomplete_details` value as JSON text. Any other or missing status extracts the text. The error is raised inside the trace session (recorded, DEC-000-47 as amended by 002). A reply that is not a mapping surfaces as a generic error (accepted, as on chat completions).
- **Reason:** The same failure kinds end a stream with `LLMError` (DEC-arch-11), so a non-streamed call reports them the same way; a cut-off answer is never mistaken for a complete one.
- **Rejected:** Returning the partial text of an incomplete reply (would differ from the stream rule of DEC-arch-11).
- **Amended:** 2026-11-08, user — the `"incomplete"` status clause and the Rejected line: an `incomplete` reply with reason `max_output_tokens` when the app set the output limit now returns the extracted text like a completed reply; with no app limit, and for every other reason, it stays `LLMError` (DEC-arch-13, which also amends the stream rule).
- **Lands in:** `llm/openai.py`, `llm/llama_swap.py` (reply extraction for `chat`, `generate`, `chat_json`)
- **Cites:** docs/architecture/interfaces.md § Exposed: error contract; docs/architecture/subsystems.md § Streaming and reasoning (non-streaming replies); DEC-arch-11; DEC-001-12; US-028.AC-1; US-009.AC-1

### DEC-003-13 — Responses stream handling: events, completion, markers and failures
- **Status:** accepted — amended by DEC-arch-13 (2026-11-08)
- **Stage:** 002.responses · **Feature:** 003.responses-chat · **Step:** 003, 005
- **Date:** 2026-11-07 · **Decided by:** planner
- **Question:** How does each Responses class turn the stream into receiver pieces, and when is a stream complete (DEC-arch-11, minus tool events)?
- **Decision:** The parser reads payload strings from `self._iter_sse_data(response)` and decodes each as JSON; non-JSON payloads (including a `[DONE]` sentinel), non-object values and objects without a string `type` are skipped. Dispatch on `type`:
  - `response.output_text.delta` → text piece (`delta`).
  - `response.reasoning_text.delta`, `response.reasoning_summary_text.delta` → reasoning piece (`delta`); no separator is inserted between reasoning or summary parts.
  - `response.completed` → the stream is complete; the parser returns at once and reads nothing further.
  - `response.failed` → `LLMError`, description `response.error.message` when a string, else `response.error` as JSON text; `response.incomplete` → `LLMError`, description `response.incomplete_details.reason` when present, else that value as JSON text; `error` → `LLMError`, description the event's `message` when a string, else the event as JSON text. No piece is delivered after a failure event.
  - Every other type (created, in_progress, output_item.added/done, content_part.*, *.done, …) is ignored.
  Empty or missing deltas deliver nothing. Markers follow DEC-000-20 per run of reasoning: the first reasoning piece after text (or at the start) is prefixed with `<think>`; the first text piece after reasoning is prefixed with `</think>`; a block still open when `response.completed` arrives is closed by delivering `</think>` as its own piece. Each piece is delivered to the receiver as it is parsed (awaited if awaitable, failures propagate unchanged, DEC-000-23) and appended to the returned text, so the return equals what the receiver got. A stream that ends without `response.completed` raises `LLMError` saying the stream ended before the reply was complete (the Responses form of DEC-001-1); a `[DONE]` sentinel does not count as completion. Reader failures map per DEC-001-7.
- **Reason:** The payload carries its own type (DEC-arch-11); `response.completed` is the protocol's only completion signal (llama.cpp sends no `[DONE]`), and per-run markers keep interleaved reasoning and text each in its own block, as the chat-completions parser does.
- **Rejected:** Reading text from `*.done` events (duplicates the deltas). Accepting `[DONE]` as completion (no Responses server is known to send it; it would hide a truncated stream).
- **Amended:** 2026-11-08, user — the `response.incomplete` clause: with reason `max_output_tokens` and an output limit set by the app, it ends the stream like `response.completed` (an open reasoning block is closed by a `</think>` piece; the return equals what the receiver got); with no app limit, and for every other reason, it stays `LLMError` (DEC-arch-13).
- **Lands in:** streamed `chat` and the Responses stream parser in `llm/openai.py`, `llm/llama_swap.py`
- **Cites:** docs/architecture/subsystems.md § Streaming and reasoning; docs/architecture/interfaces.md § Consumed: backend APIs (Responses stream format), § Streaming callback; DEC-arch-11; DEC-000-20; DEC-000-23; DEC-001-1; DEC-001-7; US-059.AC-1; US-060.AC-2; US-026.AC-1..AC-4

### DEC-003-15 — Live tests: models and environment variables
- **Status:** accepted

### DEC-003-16 — Test seams for the Responses classes

### DEC-003-17 — A keyword flag tells the Responses readers that the app set the output limit
- **Status:** accepted
- **Stage:** 002.responses · **Feature:** 003.responses-chat · **Step:** 006, 007
- **Date:** 2026-11-08 · **Decided by:** planner
- **Question:** How do the non-streamed reply reader and the chat stream parser learn whether the app set the output limit (DEC-arch-13), given neither has the settings in scope?
- **Decision:** Each Responses class's non-streamed reply reader (`_responses_reply_text`, module-level in `llm/openai.py` and in `llm/llama_swap.py`) and its chat stream parser (`_read_responses_stream` / `_stream_responses_response`) gain a keyword-only parameter `output_limit_set`, a boolean defaulting to false. The calling operation computes it after the merge as "the wire settings hold `max_output_tokens`" — the field is present exactly when the merged settings hold a non-`None` `max_tokens`, whether set as a call option or a client default, directly or through the `context_length` alias, and absent when the app set nothing or cleared a default per call with `None` (DEC-003-9, DEC-000-5). Callers: `chat` (streamed and non-streamed) and `chat_json`; `generate` through `chat`. Any caller that passes nothing keeps today's behaviour.
- **Reason:** The wire field is the merge's own verdict on whether the app set the limit, including aliases, defaults and `None` clearing; a per-call argument keeps the readers pure and leaves every existing caller and test unchanged.
- **Rejected:** Passing the whole wire settings or payload into the readers (couples the parsers to the wire dict). Storing the flag on the client (per-call state on a shared client breaks concurrent calls, US-029). Re-deriving it from the raw call options (misses client defaults, the alias and `None` clearing).
- **Lands in:** `llm/openai.py` (`_responses_reply_text`, `_read_responses_stream`, `chat`, `chat_json`); `llm/llama_swap.py` (`_responses_reply_text`, `_stream_responses_response`, `chat`, `chat_json`)
- **Cites:** DEC-arch-13; DEC-003-9; DEC-000-5; US-062.AC-1, US-062.AC-6

### DEC-003-18 — Only the exact reason max_output_tokens counts as a cut at the app's limit
- **Status:** accepted
- **Stage:** 002.responses · **Feature:** 003.responses-chat · **Step:** 006, 007
- **Date:** 2026-11-08 · **Decided by:** planner
- **Question:** When does an incomplete reply or `response.incomplete` event count as "cut at the output limit" (DEC-arch-13)?
- **Decision:** Only when its incomplete details are a mapping whose `reason` is exactly the string `"max_output_tokens"` (non-streamed: the reply's `incomplete_details`; streamed: the event's `response.incomplete_details`). Any other value (another string, a non-string, a different case), a missing `reason` and missing or null incomplete details stay `LLMError`, with the description built as before (DEC-003-12, DEC-003-13).
- **Reason:** An exact match returns text only for the one stop DEC-arch-13 names; anything else is an early end the app did not cause (US-024.AC-2).
- **Rejected:** Case-insensitive or prefix matching (no server is known to vary the value; looser matching could turn a different stop into a returned reply).
- **Lands in:** `llm/openai.py`, `llm/llama_swap.py` (reply reader, chat stream parser)
- **Cites:** DEC-arch-13; DEC-003-12; DEC-003-13; US-024.AC-2

### DEC-003-19 — A cut at the app's limit reads like a completed reply, streamed and not
- **Status:** accepted
- **Stage:** 002.responses · **Feature:** 003.responses-chat · **Step:** 006, 007
- **Date:** 2026-11-08 · **Decided by:** planner
- **Question:** What exactly does a chat-style call do with a reply cut at the app's limit (DEC-003-17 flag on, DEC-003-18 reason matches)?
- **Decision:** Non-streamed: the reader extracts and returns the text exactly as for a completed reply (DEC-003-12 extraction; `""` when there is no text). Streamed: the matching `response.incomplete` event ends the stream as `response.completed` does — a reasoning block still open is closed by a `</think>` piece of its own, the parser returns at once and reads nothing further, and the return equals what the receiver got (DEC-003-13). The operation then logs the text as the call's response and returns it, as for any completed reply; `chat_json`'s parse check with an expected shape runs as before. No warning or notice. Everything else is unchanged: flag off, any other reason, `failed` / `response.failed`, the `error` event, and a stream ending without a completion event.
- **Reason:** DEC-arch-13 treats a cut the app asked for as a normal result; reusing the completed paths keeps one rule for markers, the receiver and tracing.
- **Lands in:** `llm/openai.py`, `llm/llama_swap.py` (reply reader, chat stream parser)
- **Cites:** DEC-arch-13; DEC-003-12; DEC-003-13; DEC-000-20; DEC-000-37; US-062.AC-1, US-062.AC-2, US-062.AC-3, US-062.AC-5

# Decisions — 004.responses-tools (system)

**Stage:** 002.responses · **Feature:** 004.responses-tools

Planning-time decisions for tool conversations on the Responses protocol (OpenAI and llama-swap, streamed and not): tool flattening, call and result items, reasoning carry-over between rounds, tool-round stream parsing, and the live two-round tests. The design they realize is DEC-arch-9, DEC-arch-10 (tools part), DEC-arch-11 (tool part) and DEC-arch-12 (`arch-responses-protocol.md`). Wire evidence: llama.cpp behind llama-swap, probe of 2026-11-07, recorded in DEC-004-20; OpenAI per its documented Responses API. DEC-004-19 and DEC-004-20 were recorded at finalization (2026-11-08).

### DEC-004-1 — Flattened tools copy the app's strict flag, else send strict false
- **Status:** accepted
- **Stage:** 002.responses · **Feature:** 004.responses-tools · **Step:** 001, 003
- **Date:** 2026-11-07 · **Decided by:** user
- **Question:** Which `strict` value does a flattened Responses function tool carry?
- **Decision:** When the app's definition holds `function.strict`, that value is copied to the flat tool's `strict` unchanged. Otherwise the flat tool carries `strict: false`. A definition already in the flat shape is sent as given (DEC-004-5), so its own `strict` (or its absence) is kept.
- **Reason:** Responses function tools default to strict on OpenAI, and schemas built by `pydantic_to_openai_tool` usually do not meet the strict-mode requirements; `false` keeps today's non-strict chat-completions behaviour.
- **Rejected:** Omitting `strict` (OpenAI would apply strict mode and refuse or constrain typical schemas). Always sending `false` (would override an app that asked for strict).
- **Lands in:** tool flattening in `llm/openai.py`, `llm/llama_swap.py`
- **Cites:** docs/architecture/data-model.md § Tool definition; DEC-arch-10; US-031.AC-1

### DEC-004-5 — Tool definitions are flattened per entry; flat entries pass through
- **Status:** accepted
- **Stage:** 002.responses · **Feature:** 004.responses-tools · **Step:** 001, 003
- **Date:** 2026-11-07 · **Decided by:** planner
- **Question:** How is today's nested function-tool definition written as a Responses tool, and how are tool names read for the pre-flight and the offered check?
- **Decision:** Per entry of `tools_definitions`, in order: an entry with a `function` mapping becomes `{"type": "function", "name": <function.name>, "description": <function.description> (only when present), "parameters": <function.parameters> (only when present), "strict": <per DEC-004-1>}`. An entry without a `function` key (already in the flat shape) is sent unchanged. The flattened list is sent as `tools` on every round. The tool name used by the pre-flight check (advertised without a callable, `ValueError`) and by the offered check (DEC-002-3) is `function.name` for a nested entry and `name` for a flat entry. The app's definitions are never modified.
- **Reason:** App-facing shapes stay the same on both protocols (DEC-arch-10); passing flat entries through mirrors DEC-003-10 and keeps apps already using the Responses shape working.
- **Rejected:** Refusing flat entries (the server is the authority on what it accepts).
- **Lands in:** tool flattening and `chat_with_tools` in `llm/openai.py`, `llm/llama_swap.py`
- **Cites:** docs/architecture/data-model.md § Tool definition; docs/architecture/interfaces.md § Tool loop contract; DEC-arch-10; DEC-003-10; DEC-002-3; US-031.AC-1; US-032.AC-1

### DEC-004-6 — The loop history keeps today's turn shapes; input items are rebuilt each round
- **Status:** accepted
- **Stage:** 002.responses · **Feature:** 004.responses-tools · **Step:** 001, 003
- **Date:** 2026-11-07 · **Decided by:** planner
- **Question:** In which shape does the Responses tool loop hold its conversation, and how does each round turn it into input items?
- **Decision:** The loop's internal copy of the conversation keeps the chat-completions turn shapes (data-model § Message). A reply's tool calls are recorded on the assistant turn as `{"role": "assistant", "content": <round text>, "tool_calls": [{"id": <call_id>, "type": "function", "function": {"name": <name>, "arguments": <arguments>}}, …]}`; each result as `{"role": "tool", "content": <result text>, "tool_call_id": <call_id>}`. Each round converts the whole copy, by turn shape, in order:
  - assistant turn with `tool_calls` → the carried reasoning items attached to that turn (DEC-004-7), then `{"type": "message", "role": "assistant", "content": <content>}` only when its content is non-empty text, then one `{"type": "function_call", "call_id": <id>, "name": <name>, "arguments": <arguments as text>}` per call in order (arguments that are a mapping are sent as JSON text; missing as `""`);
  - `role: tool` turn → `{"type": "function_call_output", "call_id": <tool_call_id>, "output": <content as text>}`;
  - every other turn → the item feature 003's payload builder makes for it (DEC-003-11 as corrected, DEC-004-4).
  The rule is by shape, so a caller history that already holds tool-call and tool-result turns is converted the same way (without reasoning). The function-call item is sent without the server's item `id`. `call_id` is taken as the server sent it.
- **Reason:** One history shape on both protocols keeps the loop logic and the trace record the same; rebuilding the items each round keeps the wire translation in one place.
- **Rejected:** Keeping the history as Responses items (a second history shape and a second trace format). Re-sending the server's function-call item verbatim (probe: the reduced form is accepted; the chat-completions turn has no place for the item id). Accepted risk: if OpenAI refuses a carried reasoning item whose following function call has no item id, the item id is added to the per-call record of DEC-004-7 as a mid-flight decision — the OpenAI live two-round test is the check.
- **Lands in:** round-input conversion and `chat_with_tools` in `llm/openai.py`, `llm/llama_swap.py`
- **Cites:** docs/architecture/data-model.md § Message; docs/architecture/interfaces.md § Consumed: backend APIs; DEC-arch-10; DEC-003-11; DEC-002-5; DEC-004-20; US-030.AC-1

### DEC-004-7 — Reasoning items are carried in a per-call record attached to their round's turn
- **Status:** accepted
- **Stage:** 002.responses · **Feature:** 004.responses-tools · **Step:** 001, 002, 003, 004
- **Date:** 2026-11-07 · **Decided by:** planner
- **Question:** Where are a round's reasoning items kept between rounds, and do items without encrypted content need special handling (brief open question)?
- **Decision:** Each round's reasoning items are kept verbatim, exactly as received — non-streamed from the reply's `output`, streamed from the `response.output_item.done` event of each reasoning item (DEC-004-9) — in a record local to the one `chat_with_tools` call, kept apart from the messages and keyed by the position of that round's assistant tool-call turn in the internal copy. On every later round of the same call they are sent ahead of that turn's function-call items (DEC-004-6), in the order they appeared in the round's output. Items with empty encrypted content (local servers) are re-sent unchanged — no special handling (probe: llama.cpp accepts them verbatim and with the key removed). The final round's reasoning is not kept; the record is discarded when the call ends, normally or with an error. Nothing is written to the caller's messages or to the internal turns, and the caller's list is never mutated.
- **Reason:** DEC-arch-9 needs reasoning ahead of its function calls on later rounds; a call-local record keyed by turn keeps it out of the conversation and the answer (US-058.AC-3..AC-5).
- **Rejected:** Storing reasoning on the assistant turn (it would leak into the trace history and any reuse of the turn). Stripping `encrypted_content` or `status` from local items (no server needs it; verbatim is accepted).
- **Lands in:** `chat_with_tools` in `llm/openai.py`, `llm/llama_swap.py`
- **Cites:** docs/architecture/subsystems.md § Tool loop; DEC-arch-9; DEC-arch-7; DEC-004-20; US-058.AC-3, US-058.AC-4, US-058.AC-5

### DEC-004-8 — Reading a non-streamed tool round
- **Status:** accepted — amended by DEC-arch-13 (2026-11-08)
- **Stage:** 002.responses · **Feature:** 004.responses-tools · **Step:** 001, 003
- **Date:** 2026-11-07 · **Decided by:** planner
- **Question:** How is a non-streamed tool-round reply turned into round text, tool calls and carry items?
- **Decision:** The reply's status is checked first exactly as in DEC-003-12 (`failed` / `incomplete` → `LLMError` with the server's reason, inside the trace session). Then the `output` list is visited in order: `function_call` items become the round's tool calls in order of appearance, numbered densely from 0 (call id = `call_id`, name = `name`, arguments = `arguments` as given); `message` items give the round text per DEC-003-12 (output-text parts concatenated; null or missing → `""`); `reasoning` items are kept as carry items (DEC-004-7); every other item type is ignored. No tool calls → the round text is the answer.
- **Reason:** Same text and failure rules as the non-tool path; positions in `output` count every item, so calls are renumbered densely (DEC-arch-10).
- **Amended:** 2026-11-08, user — the status check: an `incomplete` round with reason `max_output_tokens` when the app set the output limit is read on; with no tool calls its text is the answer, with tool calls it ends with `LLMError` (arguments may be truncated, so they are not run). With no app limit, and for every other reason, `incomplete` stays `LLMError` (DEC-arch-13).
- **Lands in:** non-streamed round reading in `llm/openai.py`, `llm/llama_swap.py`
- **Cites:** docs/architecture/interfaces.md § Exposed: error contract; DEC-arch-10; DEC-003-12; US-028.AC-1; US-030.AC-3

### DEC-004-9 — A separate stream parser per class reads tool rounds
- **Status:** accepted — amended by DEC-arch-13 (2026-11-08)
- **Stage:** 002.responses · **Feature:** 004.responses-tools · **Step:** 002, 004
- **Date:** 2026-11-07 · **Decided by:** planner
- **Question:** How does a streamed tool round become receiver pieces, round text, tool calls and carry items, and does it share 003's chat parser?
- **Decision:** Each Responses class gets its own private tool-round parser, separate from 003's chat parser, which is not changed (unknown types still skipped there; its return still equals what the receiver got). The round parser reads payloads through `_iter_sse_data` and decodes them as in DEC-003-13 (non-JSON, non-object and typeless payloads skipped). Per event type:
  - `response.output_text.delta` → text piece; `response.reasoning_text.delta`, `response.reasoning_summary_text.delta` → reasoning piece. Markers per DEC-003-13 with fresh marker state each round; a block still open when the round's `response.completed` arrives is closed by a `</think>` piece, so each round's reasoning reaches the receiver closed before the next round's pieces. Pieces are delivered as parsed (awaited if awaitable; failures propagate unchanged, DEC-000-23). The round text kept for the history and the answer is the text deltas only — no reasoning, no markers.
  - `response.output_item.added` with a `function_call` item → starts a call keyed by the item's `id` (fallback `output_index`), taking `call_id`, `name` and any initial `arguments`.
  - `response.function_call_arguments.delta` → appends `delta` to the call keyed by `item_id` (fallback `output_index`); a delta for an unknown key starts a call with no name (the offered check then ends the loop with `LLMError`, DEC-002-3).
  - `response.function_call_arguments.done` and `response.output_item.done` with a `function_call` item → string `arguments` replace the assembled text; a non-empty `call_id` / `name` on the done item is set; a done item for an unknown key starts the call.
  - `response.output_item.done` with a `reasoning` item → carry item (DEC-004-7), recorded with its `output_index`.
  - `response.completed` → the round is complete; the parser returns at once.
  - `response.failed`, `response.incomplete`, `error` → `LLMError` as in DEC-003-13; stream end without `response.completed` → `LLMError` (a `[DONE]` sentinel does not count). Every other type is ignored.
  Tool calls are returned in order of first appearance, numbered densely from 0; carry items are returned ordered by `output_index` regardless of the order in which items finished (probe: reasoning's done event can arrive after the call's deltas). Tool-call fragments are never delivered to the receiver (same contract as chat completions; observing tool calls is out of scope).
- **Reason:** A separate parser keeps 003's chat contract (return equals receiver output) intact while the tool path returns text without reasoning, mirroring the two chat-completions parsers (DEC-000-33).
- **Rejected:** Extending 003's chat parser with a mode flag (couples two return contracts in one method). Using `response.completed`'s `output` for carry items (the done events already carry the full items; one source of truth per round).
- **Amended:** 2026-11-08, user — the `response.incomplete` clause: with reason `max_output_tokens` and an output limit set by the app, it ends the round like `response.completed` (an open reasoning block is closed by a `</think>` piece); a round with no tool calls is the answer, a round with tool calls ends with `LLMError`. With no app limit, and for every other reason, it stays `LLMError` (DEC-arch-13).
- **Lands in:** tool-round stream parser and streamed `chat_with_tools` in `llm/openai.py`, `llm/llama_swap.py`
- **Cites:** docs/architecture/subsystems.md § Streaming and reasoning; docs/architecture/interfaces.md § Streaming callback; DEC-arch-11; DEC-arch-10; DEC-003-13; DEC-004-20; DEC-000-20; DEC-000-22; DEC-000-23; DEC-000-33; US-023.AC-1, US-023.AC-2; US-027.AC-1, US-027.AC-2; US-058.AC-5

### DEC-004-11 — Stage 001 tool-loop rules are reproduced unchanged on both Responses classes
- **Status:** accepted
- **Stage:** 002.responses · **Feature:** 004.responses-tools · **Step:** 001, 003
- **Date:** 2026-11-07 · **Decided by:** planner
- **Question:** Which tool-loop rules hold on the Responses classes?
- **Decision:** Exactly those of the chat-completions loop after feature 002, in the same order per call: pre-flight (advertised without a callable → `ValueError` before any request); per requested call in order — offered check (DEC-002-3), argument reading (DEC-002-4), `log_tool_call`, argument-name check (`ValueError`), run (sync or awaited; a raise → `RuntimeError` naming the tool, DEC-000-26), result conversion (DEC-002-5), `log_tool_result`, result turn; round limit → `RuntimeError` containing `max_loops` and the value, raised after the trace session (DEC-002-2). Each Responses class holds its own copy (DEC-arch-2, DEC-002-1).
- **Reason:** The brief requires stage 001's tool-loop behaviour on Responses; one rule set keeps the protocols interchangeable (US-057.AC-1).
- **Note:** 2026-11-08, at finalization (confirmed: user) — the two copies differ in these deliberate ways, all allowed by DEC-arch-2 (separate copies, free to diverge); none changes a loop rule above:
  - Tool definitions: one class copies the app's definitions before flattening, the other passes them straight to the flattening; the app's list is unmodified either way (DEC-004-5).
  - Tool-call arguments that are neither text nor a mapping: one class writes them as JSON text, the other as plain `str` text.
  - Error and warning texts are backend-specific (each names its own class).
  - The per-call reasoning record (DEC-004-7): llama-swap records an empty list for a round without reasoning items; OpenAI records nothing for such a round. What is sent is the same.
  - Round-call shape handed back by the round readers: one class returns the internal assistant-turn tool-call entries, the other `{call_id, name, arguments}` records that the loop turns into those entries; the history and the wire items are the same (DEC-004-6).

### DEC-004-13 — Live tool tests: files, models, tools and settings

### DEC-004-15 — The tool-round readers take the output-limit flag; chat_with_tools computes it once per call
- **Status:** accepted
- **Stage:** 002.responses · **Feature:** 004.responses-tools · **Step:** 005, 006
- **Date:** 2026-11-08 · **Decided by:** planner
- **Question:** How do the tool-round readers, non-streamed and streamed, learn whether the app set the output limit (DEC-arch-13, tool part)?
- **Decision:** Each Responses class's non-streamed tool-round reader (`_read_responses_tool_round` in `llm/openai.py`, `_responses_tool_round` in `llm/llama_swap.py`) and its tool-round stream parser (`_read_responses_tool_stream` / `_stream_responses_tool_round`) gain the keyword-only `output_limit_set` boolean, defaulting to false. The name and meaning are the same as in DEC-003-17 / DEC-003-20. `chat_with_tools` computes it once per call, after the merge, as "the wire settings hold `max_output_tokens`". The same value is passed to the reader or parser of every round. The non-streamed reader may hand the flag on to `_responses_reply_text` (DEC-003-17) or read the status itself; either way the match is DEC-003-18. Any caller that passes nothing keeps today's behaviour.
- **Reason:** The settings are fixed for the whole call, so one computation serves every round. Reusing the chat part's name and verdict keeps the "the app set the limit" rule identical across chat and tool chat, including client defaults, the alias and per-call `None` clearing.
- **Rejected:** Re-computing the flag per round from the payload (same value, more places to diverge). Storing it on the client (per-call state on a shared client breaks concurrent calls, US-029). Passing the settings into the readers (same rejection as DEC-003-17).
- **Lands in:** `llm/openai.py` (`_read_responses_tool_round`, `_read_responses_tool_stream`, `chat_with_tools`); `llm/llama_swap.py` (`_responses_tool_round`, `_stream_responses_tool_round`, `chat_with_tools`)
- **Cites:** DEC-arch-13; DEC-003-17; DEC-003-18; DEC-003-20; DEC-004-8; DEC-004-9; US-062.AC-4, US-062.AC-6

### DEC-004-16 — A non-streamed round cut at the app's limit: the answer without tool calls, an error with them
- **Status:** accepted
- **Stage:** 002.responses · **Feature:** 004.responses-tools · **Step:** 005, 006
- **Date:** 2026-11-08 · **Decided by:** planner
- **Question:** What does the non-streamed tool loop do with a round reply whose status is `incomplete` with the matching reason while the flag of DEC-004-15 is on?
- **Decision:** The reply's `output` is read as in DEC-004-8.
  - It holds no `function_call` item → the reader returns the round with its text (extracted as for a completed reply, DEC-003-19) and no tool calls. The loop's no-calls branch then logs the text as the call's response and returns it, as for a completed answer round.
  - It holds one or more `function_call` items → the reader raises `LLMError` with the same message and description as an unmatched incomplete round (the server's reason). No tool of that round runs and no further request is sent.
  With the flag off, any other reason, missing details or a `failed` reply, the DEC-004-8 status check is unchanged.
- **Reason:** DEC-arch-13: the calls' arguments may be truncated, so they are not run. A cut round without calls is the model's answer under the app's own limit. Reusing the existing incomplete error keeps one failure shape for the app.
- **Rejected:** Running the calls whose arguments decode (a call can be missing entirely or be complete but followed by a cut one; the round is not trustworthy). Returning the round text when calls exist (it silently drops the model's tool request).
- **Lands in:** `_read_responses_tool_round` in `llm/openai.py`; `_responses_tool_round` in `llm/llama_swap.py`
- **Cites:** DEC-arch-13; DEC-004-8; DEC-003-12; DEC-003-18; DEC-003-19; US-062.AC-4, US-062.AC-6; US-024.AC-2

### DEC-004-17 — A streamed round cut at the app's limit: ends like completed without a started call, an error with one
- **Status:** accepted
- **Stage:** 002.responses · **Feature:** 004.responses-tools · **Step:** 005, 006
- **Date:** 2026-11-08 · **Decided by:** planner
- **Question:** What does the tool-round stream parser do on a `response.incomplete` event whose `response.incomplete_details.reason` matches DEC-003-18 while the flag of DEC-004-15 is on?
- **Decision:** A call counts as *started* once the parser has begun assembling it in this round, from an added `function_call` item, an arguments fragment or a done `function_call` item (DEC-004-9).
  - No call started → the round ends as at `response.completed`. A reasoning block still open is closed by a `</think>` piece of its own. The parser returns at once and reads nothing further. The round text is the text deltas only (DEC-004-9), and the loop's no-calls branch returns it as the answer.
  - A call started → the parser raises `LLMError` with the same message and description as an unmatched incomplete event (the server's reason). It delivers no further piece, not even a closing marker, so the receiver sees what it sees for any failure event. No tool of that round runs and no further request is sent.
  The cut round's carry items are not needed: a final round's reasoning is not kept (DEC-004-7). With the flag off, any other reason, `response.failed`, `error`, or a stream ending without a completion event, DEC-004-9 is unchanged.
- **Reason:** Reusing the completed path keeps one rule for markers and the receiver (as DEC-003-19 does for chat). A nameless fragment counts as a call because its arguments are exactly what may be truncated.
- **Rejected:** Closing an open reasoning block before raising (DEC-003-13 delivers nothing after a failure event; the call ends in an error anyway). Counting only calls that have a name (an arguments-only fragment would then be dropped silently and the round returned as the answer).
- **Lands in:** `_read_responses_tool_stream` in `llm/openai.py`; `_stream_responses_tool_round` in `llm/llama_swap.py`
- **Cites:** DEC-arch-13; DEC-004-9; DEC-003-13; DEC-003-18; DEC-003-19; DEC-000-20; DEC-000-23; US-062.AC-4, US-062.AC-6; US-024.AC-2

### DEC-004-18 — A cut round leaves earlier rounds and the other loop rules unchanged
- **Status:** accepted
- **Stage:** 002.responses · **Feature:** 004.responses-tools · **Step:** 005, 006
- **Date:** 2026-11-08 · **Decided by:** planner
- **Question:** How does a round cut at the app's limit interact with tools already run, the round limit, the trace and the response format?
- **Decision:**
  - Tools run in earlier rounds of the same call stay run; there is no undo, as for any later-round failure today.
  - The `LLMError` of DEC-004-16 / DEC-004-17 is raised inside the trace session, which records and re-raises it.
  - A cut answer round is an answer round. The no-calls branch comes before the round-limit check, so it returns its text even when it is the last allowed round (DEC-002-2), and it is logged as the call's response (DEC-004-10).
  - Under a response format, the cut answer is handled exactly as a completed answer is; no check is added.
  - The pre-flight, offered, argument, failing-tool and round-limit rules of DEC-004-11 are unchanged.
  - No warning or notice is given (DEC-arch-13).
- **Reason:** DEC-arch-13 changes only what a cut round means; everything else in the loop keeps one rule set on both protocols (US-057.AC-1).
- **Lands in:** `chat_with_tools` in `llm/openai.py`, `llm/llama_swap.py`
- **Cites:** DEC-arch-13; DEC-004-10; DEC-004-11; DEC-002-2; DEC-000-26; DEC-000-48; US-062.AC-4; US-024.AC-2

### DEC-004-20 — Responses tool wire evidence (probe 2026-11-07)
- **Status:** accepted
- **Stage:** 002.responses · **Feature:** 004.responses-tools · **Step:** —
- **Date:** 2026-11-07 (recorded at finalization 2026-11-08) · **Decided by:** planner (live probe of llama.cpp behind llama-swap; OpenAI per its documented Responses API)
- **Question:** Which wire facts about Responses tool rounds do the round builders and parsers of this feature (and the typed assistant item of DEC-003-11) rely on?
- **Decision:** The following observed facts are the basis of DEC-003-11, DEC-004-4, DEC-004-6, DEC-004-7 and DEC-004-9:
  - An assistant input item without `"type": "message"` is refused by llama.cpp with 400 "Cannot determine type of 'item'"; the typed item is accepted by both servers.
  - `function_call_output.output` must be text; raw JSON (a non-string value) is refused with 400.
  - llama.cpp sends no `response.function_call_arguments.done` event; OpenAI does. The parser therefore cannot depend on it and also takes the final arguments from `response.output_item.done`.
  - The `response.output_item.added` event of a function call carries its `name` and `call_id`, with `arguments` `""`.
  - Two calls in one round arrive as separate items whose events do not interleave.
  - A reasoning item's `response.output_item.added` has status `in_progress` with empty content, summary and encrypted content; the full item arrives only in its done event, which may come after the call's deltas.
  - Delta events carry `item_id`, `output_index` and `content_index`.
  - The stream has `event:` lines as well as `data:` lines; the event type is also in the data payload, which is what the parsers read (DEC-arch-11).
  - llama.cpp accepts a function-call item without the server's item `id`, and carried reasoning items verbatim or with `encrypted_content` removed.
- **Reason:** Records the evidence the tool-round decisions rest on in the decisions layer, so it outlives the plan folder it was first written in.
- **Lands in:** round-input conversion, non-streamed round reading and tool-round stream parsers in `llm/openai.py`, `llm/llama_swap.py`; streamed fixtures in `tests/test_*_responses_tools_stream.py`
- **Cites:** docs/architecture/interfaces.md § Consumed: backend APIs (Responses stream format); DEC-arch-10; DEC-arch-11; DEC-003-11; DEC-004-4; DEC-004-6; DEC-004-7; DEC-004-9

# Decisions — 002.edge-fixes (system)

**Stage:** 001.fixes · **Feature:** 002.edge-fixes

Planning-time decisions for the per-operation edge fixes: tool loop, streamed tool-call assembly, JSON-only single values, embeddings, model listing, tracing and repeated template filling. Plan: `docs/plans/002.edge-fixes/`. The `DEC-000` entries named under "Supersedes on delivery" are flipped at finalization, not now.

### DEC-002-1 — Edge fixes land in both OpenAI-family clients; Ollama is not changed
- **Status:** accepted
- **Stage:** 001.fixes · **Feature:** 002.edge-fixes · **Step:** 001, 003
- **Date:** 2026-11-07 · **Decided by:** planner (confirmed: user)
- **Question:** Which clients receive the tool-loop, embedding and model-list fixes?
- **Decision:** `OpenAIAPIClient` and `LlamaSwapAPIClient` each get every per-client fix in their own copy of the code (no shared helper is added to the base for them). `OllamaAPIClient` is not edited: its tool loop keeps raw lookup, decode and serialisation errors, its model list keeps the empty list on a malformed reply (DEC-000-41), and its embeddings are unchanged. Fixes in shared code (the tool-stream parser, the tracer, the template helper) reach Ollama unchanged in shape.
- **Reason:** The two OpenAI-family clients are separate copies by choice, and the deprecated Ollama client is observation-only.
- **Rejected:** Moving the tool-loop checks into a base helper (contradicts the separate-copies rule); fixing Ollama too (extends a deprecated client).
- **Lands in:** `llm/openai.py`, `llm/llama_swap.py`
- **Cites:** docs/architecture/subsystems.md § Backend clients; DEC-000-35; DEC-arch-2; DEC-000-41; DEC-000-42

### DEC-002-2 — The round-limit error names the limit and its value
- **Status:** accepted
- **Stage:** 001.fixes · **Feature:** 002.edge-fixes · **Step:** 001
- **Date:** 2026-11-07 · **Decided by:** planner (confirmed: user)
- **Question:** What error ends a tool conversation that reaches the round limit, and what does it say?
- **Decision:** It stays `RuntimeError`. The message states that the round limit was reached, gives the configured value, and keeps the word `max_loops` (the parameter name the app set). The counting rule and the "last round's tools still run" rule are unchanged. The raise stays outside the trace session (untraced, accepted). Supersedes on delivery: the open part of DEC-000-25.
- **Reason:** The error contract only requires the text to state the limit as the reason; keeping the type avoids breaking apps and tests that catch `RuntimeError` or match `max_loops`.
- **Rejected:** `LLMError` for the round limit (changes the error type apps already handle).
- **Lands in:** `chat_with_tools` in `llm/openai.py`, `llm/llama_swap.py`
- **Cites:** docs/architecture/interfaces.md § Tool loop contract, § Exposed: error contract (round limit exhausted); US-034.AC-3; DEC-000-25

### DEC-002-3 — A requested tool that was not offered raises LLMError
- **Status:** accepted
- **Stage:** 001.fixes · **Feature:** 002.edge-fixes · **Step:** 001
- **Date:** 2026-11-07 · **Decided by:** planner (confirmed: user)
- **Question:** What counts as "offered", and what happens when the model asks for another tool?
- **Decision:** "Offered" means advertised in `tools_definitions`. For each requested call, in order, before its arguments are read: a missing or empty name, or a name not advertised, raises `LLMError` whose message names the requested tool (or says the name was empty) — even when `tools` holds a callable under that name. The tool is not run. Calls earlier in the same reply have already run and keep their effects. The pre-flight "advertised tool without a callable" `ValueError` is unchanged. Supersedes on delivery: the open part of DEC-000-28.
- **Reason:** Running an unadvertised callable would let the model reach functions the app did not offer; checking per call in order keeps the existing sequential semantics.
- **Rejected:** Checking only against the `tools` mapping (would run extra callables the app never advertised); validating every call of a reply before running any (changes the sequential run order, no story asks for it).
- **Lands in:** `chat_with_tools` in `llm/openai.py`, `llm/llama_swap.py`
- **Cites:** docs/architecture/interfaces.md § Tool loop contract, § Exposed: error contract (tool requested that was not offered); US-035.AC-1; US-032.AC-1; DEC-000-28

### DEC-002-4 — Unreadable tool arguments raise LLMError
- **Status:** accepted
- **Stage:** 001.fixes · **Feature:** 002.edge-fixes · **Step:** 001
- **Date:** 2026-11-07 · **Decided by:** planner (confirmed: user)
- **Question:** When are the model's tool arguments unreadable, and how is that reported?
- **Decision:** Missing or empty arguments still mean no arguments. A mapping is used as given. Text that does not decode as JSON, text that decodes to anything other than a JSON object, and any other value that is neither text nor a mapping raise `LLMError` whose message names the tool and whose description carries the original reason; it is chained from the decode error where there is one. The tool is not run. The argument-name check against the callable's signature still raises `ValueError` (DEC-000-27, accepted part). Supersedes on delivery: the open part of DEC-000-27.
- **Reason:** A tool is called with keyword arguments, so only a mapping is usable; one library error kind covers every unusable form.
- **Rejected:** Treating JSON `null` as no arguments (no server is known to send it; a silent fallback would hide a broken reply).
- **Lands in:** `chat_with_tools` in `llm/openai.py`, `llm/llama_swap.py`
- **Cites:** docs/architecture/interfaces.md § Tool loop contract, § Exposed: error contract (tool arguments unreadable); US-035.AC-2; US-033.AC-2, US-033.AC-4; DEC-000-27

### DEC-002-5 — An unserialisable tool result raises LLMError
- **Status:** accepted
- **Stage:** 001.fixes · **Feature:** 002.edge-fixes · **Step:** 001
- **Date:** 2026-11-07 · **Decided by:** planner (confirmed: user)
- **Question:** What happens when a tool's result cannot be turned into text for the model?
- **Decision:** A mapping or list result is serialised as today (JSON text, non-ASCII kept); when serialisation fails (type or value error) the call raises `LLMError` whose message names the tool, chained from the serialisation error. Any other result is still converted with `str()`. A tool that raises still ends with `RuntimeError` naming the tool (DEC-000-26); serialisation stays outside that wrap so the two kinds stay distinct. Supersedes on delivery: the open part of DEC-000-29.
- **Reason:** The tool ran correctly; the failure is the library's conversion, so the library's error is the right kind.
- **Rejected:** Falling back to `str()` for unserialisable mappings (the model would receive a Python repr silently).
- **Lands in:** `chat_with_tools` in `llm/openai.py`, `llm/llama_swap.py`
- **Cites:** docs/architecture/interfaces.md § Tool loop contract, § Exposed: error contract (tool result not serialisable); US-035.AC-3; DEC-000-26; DEC-000-29

### DEC-002-6 — Streamed tool-call fragments are told apart by position, call id and name
- **Status:** accepted
- **Stage:** 001.fixes · **Feature:** 002.edge-fixes · **Step:** 002
- **Date:** 2026-11-07 · **Decided by:** planner (confirmed: user; positionless id rule refined by planner)
- **Question:** How does the tool-stream parser assemble fragments that lack a position, or that repeat the name in every fragment?
- **Decision:** In `_stream_openai_tools_response`, per round:
  - A fragment with an integer position belongs to the call at that position, as today. Its truthy id is set; its non-empty name is **set, not appended** (a repeated identical name changes nothing); its argument text is appended.
  - A fragment without a position is matched against the current positionless call (the last one started). It starts a new call when it carries an id different from the current call's non-empty id, or when it carries no id but a non-empty name while the current call already has a name. A fragment carrying the same id as the current call continues it (its name is set, so a repeated name is harmless). Otherwise it continues the current call; with no current call it starts one.
  - Returned order: positioned calls sorted by position, then positionless calls in order of appearance. Each call keeps today's shape (id, type, function name and argument text).
  Supersedes on delivery: the open part of DEC-000-32.
- **Reason:** Call ids and names are the only identity a positionless stream carries; letting a matching id win keeps a server that repeats both id and name in every fragment working.
- **Rejected:** The briefing's literal rule "a name on a call that already has one always starts a new call" (it splits a positionless call whose fragments repeat both id and name). A positionless stream that repeats the name in every fragment without ids stays indistinguishable from consecutive calls of one tool and is split per named fragment (accepted limit; no known server does this).
- **Lands in:** `llm/llm_client.py` (`_stream_openai_tools_response`)
- **Cites:** docs/architecture/interfaces.md § Consumed: backend APIs (SSE stream format, chat completions); US-035.AC-4; DEC-000-22; DEC-000-32; DEC-001-1; DEC-001-9

### DEC-002-7 — chat_json drops the no-op field loop
- **Status:** accepted
- **Stage:** 001.fixes · **Feature:** 002.edge-fixes · **Step:** 003
- **Date:** 2026-11-07 · **Decided by:** planner (confirmed: user)
- **Question:** How is the false "not valid JSON" report for a single JSON value removed?
- **Decision:** The loop over the expected shape's `properties` in OpenAI `chat_json` is deleted; the check is only the JSON parse (DEC-000-37), so any valid JSON value — number, boolean, null, string, list or object — is returned unchanged. llama-swap has no such loop and only needs verifying. The expected shape is still not sent (US-040, out of scope). Supersedes on delivery: the field-check part of DEC-000-38 (the "not sent" part stays open).

- **Lands in:** `chat_json` in `llm/openai.py`

### DEC-002-8 — Embedding replies are checked and ordered by index
- **Status:** accepted
- **Stage:** 001.fixes · **Feature:** 002.edge-fixes · **Step:** 003
- **Date:** 2026-11-07 · **Decided by:** planner (confirmed: user)
- **Question:** What does `embed_batch` check in an embeddings reply, and in what order are vectors returned?
- **Decision:** Where `embed_batch` reads the reply (OpenAI and llama-swap), the reply must be a mapping with a list under `data`; every entry a mapping whose `embedding` is a non-empty list; the number of entries equal to the number of texts. When every entry carries an integer `index` (booleans do not count), the indices must be exactly 0..n-1 and vectors are returned in index order; otherwise they are returned in the server's order. Any violation raises `LLMError` naming the backend and what was wrong. The existing message for a reply without `data` is kept. The checks run inside the trace session, before the response is recorded. The empty batch is unchanged (still sent; US-042.AC-4 out of scope). Vector elements are not type-checked. Supersedes on delivery: the open defect parts of DEC-000-40 (not the empty-batch gap).
- **Reason:** Position numbers are the only reliable link between a vector and its text; a count check is what makes "one vector per text" hold.
- **Rejected:** Always trusting server order (the defect); sorting by index when only some entries carry one (ambiguous, so server order is kept).
- **Lands in:** `embed_batch` in `llm/openai.py`, `llm/llama_swap.py`
- **Cites:** docs/architecture/interfaces.md § Exposed: client method contract (`embed_batch` row), § Exposed: error contract (malformed embeddings reply); US-042.AC-2, US-042.AC-3, US-042.AC-5; US-043.AC-3; US-041.AC-2; DEC-000-40

### DEC-002-9 — Model-list replies are checked entry by entry
- **Status:** accepted
- **Stage:** 001.fixes · **Feature:** 002.edge-fixes · **Step:** 003
- **Date:** 2026-11-07 · **Decided by:** planner (confirmed: user)
- **Question:** What do `list_models` and `get_models` check, and does `get_models` also require an id?
- **Decision:** On OpenAI and llama-swap, both methods require a mapping with a list under `data` and every entry to be a mapping with a non-empty string `id`; otherwise `LLMError`. `list_models` returns the ids in server order; `get_models` returns the entries unchanged. The existing messages for a reply without `data` are kept. Listing stays untraced. Supersedes on delivery: the open defect part of DEC-000-41.
- **Reason:** US-046.AC-2 calls a nameless entry a malformed list for any model request; one rule for both methods means a list accepted by one is accepted by the other.
- **Rejected:** Requiring only a mapping in `get_models` (a record without an id could pass `get_models` and then fail `list_models`).
- **Lands in:** `list_models`, `get_models` in `llm/openai.py`, `llm/llama_swap.py`
- **Cites:** docs/architecture/interfaces.md § Exposed: client method contract (`list_models`, `get_models` rows), § Exposed: error contract (malformed model list); US-046.AC-2; US-044.AC-1; US-045.AC-1; DEC-000-41

### DEC-002-10 — Unreadable 2xx bodies on listing and embeddings are mapped at the call site
- **Status:** accepted
- **Stage:** 001.fixes · **Feature:** 002.edge-fixes · **Step:** 003
- **Date:** 2026-11-07 · **Decided by:** planner (confirmed: user)
- **Question:** Where does a successful reply that is not readable JSON become `LLMError` for model listing and embeddings?
- **Decision:** In `embed_batch`, `list_models` and `get_models` (OpenAI and llama-swap), not in `_request`. A JSON decode failure raised by `_request` (`json.JSONDecodeError`, `aiohttp.ContentTypeError`) is caught around that call and re-raised as `LLMError` chained from it; a non-JSON body (returned as bytes) or any non-mapping value fails the shape checks of DEC-002-8 / DEC-002-9. `LLMError` raised by `_request` (non-2xx, transport) passes through unchanged. `_request` is not edited (feature 001's territory; chat-style calls keep the accepted generic error).
- **Reason:** The error contract maps unreadable bodies only for listing and embeddings; mapping in `_request` would change every chat-style call and the deprecated Ollama paths.
- **Rejected:** Mapping in `_request` (changes accepted chat-style behaviour and collides with feature 001's changes).
- **Lands in:** `embed_batch`, `list_models`, `get_models` in `llm/openai.py`, `llm/llama_swap.py`
- **Cites:** docs/architecture/interfaces.md § Exposed: error contract (2xx reply that is not JSON); US-043.AC-4; US-046.AC-3; DEC-001-7; DEC-000-11

### DEC-002-11 — A trace record that cannot be set up leaves the call untraced
- **Status:** accepted
- **Stage:** 001.fixes · **Feature:** 002.edge-fixes · **Step:** 004
- **Date:** 2026-11-07 · **Decided by:** planner (confirmed: user)
- **Question:** What happens when the date folder cannot be created or the record file cannot be opened?
- **Decision:** In `LLMTracer.trace`, an `OSError` while creating the date folder or opening the record file (after the collision retries of DEC-002-13) makes the scope yield the shared no-op session; the call proceeds untraced and nothing is reported. Only the setup is guarded: exceptions raised by the caller's body are never treated as setup failures. Supersedes on delivery: the unwritable-folder part of DEC-000-47.
- **Reason:** Tracing is a debugging aid and must never change a call's outcome.
- **Rejected:** Emitting a warning on setup failure (no story asks for a signal; the user asked for "quietly").
- **Lands in:** `llm/trace.py` (`LLMTracer.trace`)
- **Cites:** docs/architecture/subsystems.md § Tracer (`LLMTracer`); US-050.AC-2; DEC-000-47; DEC-000-48

### DEC-002-12 — A trace write failure stops the record, never the call
- **Status:** accepted
- **Stage:** 001.fixes · **Feature:** 002.edge-fixes · **Step:** 004
- **Date:** 2026-11-07 · **Decided by:** planner (confirmed: user)
- **Question:** What happens when writing to an open record fails, including while the call's error or the footer is written?
- **Decision:** A `TraceSession` whose write fails (any `Exception`) marks itself broken and skips every later write quietly; the header write in its constructor is covered too. In `LLMTracer.trace`, recording the caller's error and writing the footer are each guarded so nothing they raise replaces the caller's result or error, and the file is closed in every case (its close guarded too). The caller's exception is re-raised unchanged. `CancelledError` handling is unchanged: no ERROR section, footer attempted, file closed. The public shape of `LLMTracer` and the session's logging methods is unchanged. Supersedes on delivery: the write-failure part of DEC-000-47.
- **Reason:** The app must always receive its call's own outcome, and a broken record must not leak the file.
- **Rejected:** Re-raising the trace error after the call's error (hides nothing but still changes the outcome on success paths).
- **Lands in:** `llm/trace.py` (`TraceSession`, `LLMTracer.trace`)
- **Cites:** docs/architecture/subsystems.md § Tracer (`LLMTracer`); US-050.AC-3, US-050.AC-1, US-050.AC-4; DEC-000-46; DEC-000-47

### DEC-002-13 — Record files are created exclusively with a counter suffix on collision
- **Status:** accepted
- **Stage:** 001.fixes · **Feature:** 002.edge-fixes · **Step:** 004
- **Date:** 2026-11-07 · **Decided by:** planner (confirmed: user)
- **Question:** How do two sessions that start in the same microsecond get separate records?
- **Decision:** The record file is opened with exclusive create. On `FileExistsError` the name gains a counter suffix before the extension — `llm-trace-<timestamp>-1.log`, `-2`, … — until a free name is found, with at most 1000 suffixed attempts; exhausting them counts as a setup failure (DEC-002-11). The first record of an instant keeps today's name. Supersedes on delivery: DEC-000-45.
- **Reason:** Exclusive create makes the name check atomic, and a suffix keeps the timestamp sortable and the layout recognisable.
- **Rejected:** A random or process-id suffix on every name (changes every file name, not only colliding ones); an unbounded retry loop (no termination guarantee on a misbehaving filesystem).
- **Lands in:** `llm/trace.py` (`LLMTracer.trace`)
- **Cites:** docs/architecture/subsystems.md § Tracer (`LLMTracer`); docs/architecture/data-model.md § Trace record; US-051.AC-1; US-048.AC-1; DEC-000-44; DEC-000-45

### DEC-002-14 — The tracer drops the inserted system message from the history
- **Status:** accepted
- **Stage:** 001.fixes · **Feature:** 002.edge-fixes · **Step:** 004
- **Date:** 2026-11-07 · **Decided by:** planner (confirmed: user)
- **Question:** How does the system instruction appear only once in a record, and how is the inserted message told apart from the caller's own system messages?
- **Decision:** Inside `TraceSession`: when the session's system instruction was logged with a non-empty text, the message-history section skips the first message only if it has the system role and exactly that text — the copy the clients insert. Any other system message (including the caller's own) is written. The SYSTEM PROMPT section stays; an empty instruction still writes an empty section (accepted). The REQUEST payload is still written verbatim, because it is what was sent. No client call site changes, so the deprecated Ollama client gets the same record without being edited, and the folder convention "log system, then messages" is unchanged. Supersedes on delivery: DEC-000-49.
- **Reason:** Every client prepends an exact copy of a truthy instruction at index 0 and logs the instruction first, so the session can recognise it without changing any call site.
- **Rejected:** Logging the caller's messages instead of the prepended copy at each call site (ten call sites, including deprecated Ollama ones); dropping the SYSTEM PROMPT section (the history would then be the only place it shows, and only when it was sent); redacting the instruction from REQUEST (the record would no longer show the request as sent).
- **Lands in:** `llm/trace.py` (`TraceSession.log_system`, `TraceSession.log_messages`)
- **Cites:** docs/architecture/data-model.md § Trace record; US-049.AC-6, US-049.AC-2, US-049.AC-10, US-049.AC-11; DEC-000-49

### DEC-002-15 — Repeated filling stops after a pass that changes nothing
- **Status:** accepted
- **Stage:** 001.fixes · **Feature:** 002.edge-fixes · **Step:** 005
- **Date:** 2026-11-07 · **Decided by:** planner (confirmed: user)
- **Question:** When does `recursive_format_placeholders` stop?
- **Decision:** It stops when no slot is found or when a whole pass leaves the text unchanged (only unknown slots remain, or a slot refers to itself). The cap of 10 passes stays and still ends silently. A self-referencing slot is still returned in the text without an error. Callable values are still evaluated per occurrence per pass. The helper stays module-only (export out of scope). Supersedes on delivery: DEC-000-52.
- **Reason:** "Nothing more can be filled" is exactly a pass that changes nothing; the cap stays as the guard against values that keep growing.
- **Lands in:** `llm/llm.py` (`recursive_format_placeholders`)

### DEC-002-16 — Trace test seams: module-level open and clock
- **Status:** accepted
- **Stage:** 001.fixes · **Feature:** 002.edge-fixes · **Step:** 004
- **Date:** 2026-11-07 · **Decided by:** planner
- **Question:** How do unit tests freeze the record clock and force record write failures without touching the filesystem's permissions?
- **Decision:** `llm/trace.py` keeps taking the session time through its module-level `datetime` name (`datetime.now(timezone.utc)`), and opens the record file with the builtin `open` looked up through the module (not `pathlib.Path.open` or `os.open`). Tests replace `llm.trace.datetime` with a frozen clock and may replace `llm.trace.open` to return a file object whose writes fail. Tests enable tracing with `monkeypatch.setenv` and a `tmp_path` folder before building the client or `LLMTracer`.
- **Reason:** Deterministic collision and failure tests need both seams; they cross the source and test folders, so they are recorded here.
- **Lands in:** `llm/trace.py`; `tests/test_llm_trace.py`
- **Cites:** US-051.AC-1; US-050.AC-2, US-050.AC-3; DEC-000-4

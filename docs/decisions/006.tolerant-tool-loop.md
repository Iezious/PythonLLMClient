# Decisions — 006.tolerant-tool-loop

**Stage:** — · **Feature:** 006.tolerant-tool-loop (release 0.2.1; not roadmapped)

Planning-time decisions for feature 006. They sit below the architecture in `docs/architecture/` and below the architect-session decisions DEC-arch-14..28 (`arch-tool-loop-0-2-1.md`), which bind this feature and are cited, not restated.

### DEC-006-1 — mypy configuration: strict in pyproject, Ollama silenced per module, mypy in the dev extra
- **Status:** accepted
- **Stage:** — · **Feature:** 006.tolerant-tool-loop · **Step:** 002
- **Date:** 2026-11-09 · **Decided by:** planner
- **Question:** How is the DEC-arch-22 gate configured so that it can run from step 002 on and stays meaningful with the deprecated module excluded?
- **Decision:** `pyproject.toml` gains a `[tool.mypy]` table with `strict = true`, `python_version = "3.11"` and `packages = ["llm"]`, and one `[[tool.mypy.overrides]]` entry for `module = "llm.ollama"` with `ignore_errors = true`. `mypy>=1.11` joins the `dev` extra; `uv.lock` is refreshed. The gate command is `uv run mypy --strict llm` (identical result to `uv run mypy` with the table). From step 002 on, every step leaves the gate green.
- **Reason:** The Ollama module is imported by the factory and the package root, so it must stay analysable; a per-module `ignore_errors` silences its own errors while an `exclude` would not stop mypy following the import.
- **Rejected:** `exclude = ["llm/ollama.py"]` (ignored for imported modules); fixing Ollama's errors (the module is not extended, DEC-arch-22).
- **Lands in:** `pyproject.toml` (`[project.optional-dependencies] dev`, `[tool.mypy]`, `[[tool.mypy.overrides]]`), `uv.lock`
- **Cites:** docs/architecture/interfaces.md § Exposed: typing contract; DEC-arch-22

### DEC-006-2 — The typing contract is checked by a unit test that runs mypy on the package and on a sample app
- **Status:** accepted
- **Stage:** — · **Feature:** 006.tolerant-tool-loop · **Step:** 002 (extended in 009)
- **Date:** 2026-11-09 · **Decided by:** planner
- **Question:** How does the automated suite prove "an app checked by a strict type checker uses the library without type errors"?
- **Decision:** `tests/test_typing_contract.py` runs mypy in a subprocess (`sys.executable -m mypy`, working directory = repository root so `llm` resolves from the source tree) twice: once as `--strict llm` (must report no errors) and once in strict mode on a small sample application module the test writes to `tmp_path`, which uses the public surface the typing contract names (usage scope returning the class's own type, per-class `options` / `default_options`, factory result `LLMClient[Any]`, tool-chat messages carrying tool-call turns; from step 009 also `tool_errors` and a typed `on_tool_event` observer on a factory-built client). The test is not skipped: mypy is in the `dev` extra (DEC-006-1). Because it is in the default run, any later step that breaks typing fails it.
- **Reason:** A static guarantee is otherwise only checked by hand; running the real checker in the suite makes it a regression gate without a CI.
- **Rejected:** A `[manual/live]` command check only (not repeated by later steps); `reveal_type`-style snapshot tests (brittle across mypy versions).
- **Lands in:** `tests/test_typing_contract.py`
- **Cites:** docs/architecture/interfaces.md § Exposed: typing contract; docs/product/features.md Cross-feature rules (strict type checker)

### DEC-006-3 — Tool-event types live in a new module; the error kind and the observer warning live in exceptions
- **Status:** accepted
- **Stage:** — · **Feature:** 006.tolerant-tool-loop · **Step:** 001
- **Date:** 2026-11-09 · **Decided by:** planner
- **Question:** Where are the new public data definitions declared?
- **Decision:** `ToolEvent` and `ToolErrorKind` are declared in a new module `llm/tool_events.py`. `LLMErrorKind` and `LLMToolObserverWarning` are declared in `llm/exceptions.py` next to `LLMError` and `LLMSettingIgnoredWarning`. All four are re-exported from `llm/__init__.py` and listed in `__all__`. These are data and contract definitions only; no behaviour lives in either module (DEC-arch-15).
- **Reason:** The error kind belongs to the error it qualifies; the tool-event shapes are used by four independent classes and need one definition that none of them owns.
- **Rejected:** Putting the tool-event shapes in `llm/message.py` (that module is the conversation message shape) or in `llm/llm_client.py` (the base holds transport plumbing only).
- **Lands in:** `llm/tool_events.py`, `llm/exceptions.py`, `llm/__init__.py`
- **Cites:** docs/architecture/data-model.md § Tool events, § Error kinds; docs/architecture/interfaces.md § Exposed: warnings; DEC-arch-19

### DEC-006-4 — ToolEvent is a total typed dictionary; how arguments and the call id are filled
- **Status:** accepted
- **Stage:** — · **Feature:** 006.tolerant-tool-loop · **Step:** 001 (shape), 006–009 (filling)
- **Date:** 2026-11-09 · **Decided by:** planner
- **Question:** Are the "none otherwise" fields of `ToolEvent` absent or present-as-none, and how are `arguments` and `call_id` normalised from what the server sent?
- **Decision:** `ToolEvent` is a total `TypedDict`: all six keys (`type`, `name`, `call_id`, `arguments`, `output`, `error_kind`) are present in every event, with `None` where the data model says none. `arguments`: a string is passed verbatim; missing (`None`) becomes `""`; any other value (a mapping, or anything else the server sent) is `json.dumps(value, ensure_ascii=False)`, falling back to `str(value)` when it is not JSON-serialisable. `call_id`: the server's id for the call when it is a non-empty string, otherwise `None`. `name`: the requested name as sent (an empty name stays `""`). Each of the four classes fills the event in its own loop.
- **Reason:** A total shape lets an observer read every key without guards; verbatim strings keep "exactly as the model sent them", and non-ASCII-preserving JSON is the closest text form of a mapping.
- **Rejected:** A non-total `TypedDict` with absent keys (forces `.get` in every observer).
- **Lands in:** `llm/tool_events.py`; the tool loops of `llm/openai.py`, `llm/llama_swap.py`, `llm/openai_chat_completions.py`, `llm/llama_swap_chat_completions.py`
- **Cites:** docs/architecture/data-model.md § Tool events; US-065.AC-1, US-065.AC-3

### DEC-006-5 — New constructor and factory arguments are keyword-only and follow the existing ones
- **Status:** accepted
- **Stage:** — · **Feature:** 006.tolerant-tool-loop · **Step:** 003, 004
- **Date:** 2026-11-09 · **Decided by:** planner
- **Question:** Where and how do `read_timeout` and `trace` enter the constructors and the factory?
- **Decision:** On `LLMClient.__init__` and the four OpenAI-family constructors, `read_timeout` and `trace` are keyword-only, after `default_options`, both defaulting to `None`. `OllamaAPIClient.__init__` gains only `trace`, keyword-only, defaulting to `None`, passed to the base. On `get_llm_client`, `read_timeout` then `trace` follow `protocol`, keyword-only, defaulting to `None`, and are forwarded by keyword. `protocol` therefore is no longer the factory's last argument; this refines the position stated in DEC-003-8 (its "None means not passed" rule is unchanged) — flagging it for the architect at finalization.
- **Reason:** Keyword-only arguments cannot be shifted by an existing positional call, and the order matches docs/architecture/interfaces.md § Exposed: factory.
- **Rejected:** Positional-or-keyword new arguments (an existing positional call could bind the wrong slot later).
- **Lands in:** `llm/llm_client.py`, `llm/openai.py`, `llm/llama_swap.py`, `llm/openai_chat_completions.py`, `llm/llama_swap_chat_completions.py`, `llm/ollama.py` (`trace` only), `llm/llm.py`
- **Cites:** docs/architecture/interfaces.md § Exposed: constructor arguments, § Exposed: factory; DEC-arch-20; DEC-arch-24; DEC-arch-27; DEC-003-8

### DEC-006-6 — The trace switch is resolved inside trace.py through a private construction path
- **Status:** accepted
- **Stage:** — · **Feature:** 006.tolerant-tool-loop · **Step:** 004
- **Date:** 2026-11-09 · **Decided by:** planner
- **Question:** Where is the three-state `trace` argument (DEC-arch-27) turned into an enabled or disabled tracer, without changing the public `LLMTracer` surface?
- **Decision:** `llm/trace.py` gains a private construction path (a private class method or module-private function, named by the skeleton) that takes the switch value and returns an `LLMTracer`: `None` → exactly today's environment read; `False` → disabled; `True` → enabled with the folder from `LLM_TRACE_FOLDER`, `LLM_TRACE` not consulted, and `ValueError` naming the missing folder variable when that variable is unset or empty. The public `LLMTracer()` constructor keeps its current call shape and behaviour. The base constructor builds its tracer through this path once, so the refusal surfaces at client creation.
- **Reason:** The tracer is a supported public surface whose constructor shape the architecture does not extend; a private path realizes DEC-arch-27 without a public contract change.
- **Rejected:** A new public constructor argument on `LLMTracer` (an unagreed public-surface change); resolving the switch in the base by patching tracer attributes (couples the base to tracer internals).
- **Lands in:** `llm/trace.py`, `llm/llm_client.py`
- **Cites:** docs/architecture/subsystems.md § Tracer; docs/architecture/interfaces.md § Exposed: constructor arguments, § Exposed: utilities; DEC-arch-27; DEC-000-4

### DEC-006-7 — Tool calls in the trace: one call entry per call, the model text as result, then a tool-error note
- **Status:** accepted
- **Stage:** — · **Feature:** 006.tolerant-tool-loop · **Step:** 004 (entry), 006–009 (use)
- **Date:** 2026-11-09 · **Decided by:** planner
- **Question:** Which trace entries does a tolerant-mode failure or an observer failure produce, and in which order?
- **Decision:** The trace session gains one entry method, `log_tool_error(name, note)`, writing a `TOOL ERROR: <name>` section with the note text. In every class's loop: the `TOOL CALL: <name>` entry is written once per call before the tool would run (or before its failure is recorded), carrying the parsed arguments when they were read, otherwise the raw argument text. A tolerant tool failure writes `TOOL RESULT: <name>` with the model-facing text (DEC-arch-14), then `TOOL ERROR: <name>` with the failure kind name (`not_offered`, …). A tolerant observer failure writes `TOOL RESULT: <name>` with the observer-failure text, then `TOOL ERROR: <name>` with the note `observer failed: <ExceptionType>: <message>`. Strict-mode failures are recorded as today (the `ERROR` section of the traced scope). Trace write failures keep DEC-002-12.
- **Reason:** The record must show what the model was told and why (DEC-arch-21); a dedicated section keeps the note distinct from the result text the model received.
- **Rejected:** Appending the note to the result text (the record would no longer show the model's text verbatim); reusing the `ERROR` section (reserved for the exception that ends the traced scope).
- **Lands in:** `llm/trace.py` (session entry method); the tool loops of the four OpenAI-family modules
- **Cites:** docs/architecture/data-model.md § Trace record; docs/architecture/subsystems.md § Tracer; DEC-arch-21; DEC-002-12; US-065.AC-13

### DEC-006-8 — Tolerant observer failure: the observer-failure text replaces the call's output; one warning per failure
- **Status:** accepted
- **Stage:** — · **Feature:** 006.tolerant-tool-loop · **Step:** 006–009
- **Date:** 2026-11-09 · **Decided by:** planner
- **Question:** In tolerant mode, what does the model receive when the observer fails on a `result` or an `error` event (the tool already ran or already failed), and how often is the warning emitted?
- **Decision:** Whatever event the observer fails on, the call's tool-result carries the observer-failure text `Tool '<n>' failed.` (DEC-arch-14), replacing the result text or the failure-kind text that call would otherwise have carried; a result already produced is discarded. Failing on `start` means the tool is not run. `LLMToolObserverWarning` is emitted once per observer failure (no once-per-client rule), its message naming the tool, the event type the observer failed on, and the observer's exception type and message. The loop then goes on with the next call.
- **Reason:** DEC-arch-14 fixes one text for an observer failure and the architecture says the model is told the tool failed; each failure is a distinct incident the app may want to see.
- **Rejected:** Keeping the tool's real result when the observer fails on `result` (contradicts "the model is told the tool failed"); a once-per-client warning (hides repeated observer faults).
- **Lands in:** the tool loops of `llm/openai.py`, `llm/llama_swap.py`, `llm/openai_chat_completions.py`, `llm/llama_swap_chat_completions.py`
- **Cites:** docs/architecture/interfaces.md § Tool event observer, § Exposed: warnings; DEC-arch-14; DEC-arch-26; US-065.AC-8, US-065.AC-9, US-065.AC-11

### DEC-006-9 — tool_errors is not validated at run time; only "raise" selects strict handling
- **Status:** accepted
- **Stage:** — · **Feature:** 006.tolerant-tool-loop · **Step:** 006–009
- **Date:** 2026-11-09 · **Decided by:** planner
- **Question:** What happens when `tool_errors` holds a value outside its declared literal type?
- **Decision:** No run-time check. Each class selects strict handling exactly when `tool_errors == "raise"`; every other value behaves as the default `"result"`. The declared literal type is the contract, enforced by the type checker.
- **Reason:** The error contract defines no refusal for an invalid value; adding one would be a new error behaviour, and the default is the tolerant mode anyway.
- **Rejected:** `ValueError` on an unknown value (an error case the architecture does not list).
- **Lands in:** the `chat_with_tools` of the four OpenAI-family modules
- **Cites:** docs/architecture/interfaces.md § Tool failures; DEC-arch-28

### DEC-006-10 — The base chat_with_tools stub gains tool_errors and on_tool_event in the last tool-loop step
- **Status:** accepted
- **Stage:** — · **Feature:** 006.tolerant-tool-loop · **Step:** 009
- **Date:** 2026-11-09 · **Decided by:** planner
- **Question:** When does the base `LLMClient.chat_with_tools` declaration gain the two new parameters, given the strict type gate must stay green between steps?
- **Decision:** The base declaration (which still raises `NotImplementedError`) gains `tool_errors` and `on_tool_event`, with the same types and defaults as the classes, in step 009, after all four OpenAI-family classes declare them. Until then each class adds them as extra keyword-only parameters, which a strict checker accepts as a compatible override. The deprecated Ollama override does not gain them (DEC-arch-24); its resulting override mismatch is silenced by DEC-006-1.
- **Reason:** The method contract defines `chat_with_tools` with both parameters on `LLMClient`, so a factory-built `LLMClient[Any]` must accept them; adding them earlier would make the not-yet-converted classes incompatible overrides and break the gate mid-feature.
- **Rejected:** Adding them to the base in step 002 (three classes would fail the gate until their steps).
- **Lands in:** `llm/llm_client.py`
- **Cites:** docs/architecture/interfaces.md § Exposed: client method contract, § Exposed: typing contract; DEC-arch-24; DEC-006-1

### DEC-006-11 — Silence-limit tests run against an in-process aiohttp server, with fixed timings
- **Status:** accepted
- **Stage:** — · **Feature:** 006.tolerant-tool-loop · **Step:** 003
- **Date:** 2026-11-09 · **Decided by:** planner
- **Question:** How is "a stream silent longer than the limit ends; a stream that keeps producing finishes" checked without a live backend, given the per-read limit is enforced inside the HTTP library?
- **Decision:** Besides seam tests that check which time limits each request is opened with, `tests/test_llm_read_timeout.py` starts an `aiohttp.web` server in-process on `127.0.0.1` with an ephemeral port (no new dependency; `aiohttp.web` ships with `aiohttp`) serving a chat-completions SSE stream. Timings: silence limit 0.2 s; the "keeps producing" stream sends a frame every 0.05 s for at least 0.5 s in total, then completes; the "silent" stream sends one frame and then pauses 1.0 s; the total limit stays at a value well above both (for example 30 s). No live server is used.
- **Reason:** The silence limit is enforced by the HTTP library while reading, which a monkeypatched seam cannot exercise; a local server gives a real read path while staying deterministic enough with a 4x margin.
- **Rejected:** Seam-only tests (cannot show AC-2); live-server tests (cannot make a real backend go silent on demand).
- **Lands in:** `tests/test_llm_read_timeout.py`
- **Cites:** US-068.AC-1, US-068.AC-2, US-068.AC-3; DEC-arch-20

### DEC-006-13 — Ollama: bound to its settings shape in the class header and passes trace through; nothing else changes
- **Status:** accepted
- **Stage:** — · **Feature:** 006.tolerant-tool-loop · **Step:** 002, 004
- **Date:** 2026-11-09 · **Decided by:** planner
- **Question:** Which edits does the deprecated `llm/ollama.py` receive in this feature?
- **Decision:** Exactly two: its class header binds the generic base to its own settings shape (step 002, typing only), and its constructor accepts `trace` and passes it to the base (step 004, DEC-arch-24, DEC-006-5).

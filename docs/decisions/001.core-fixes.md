# Decisions — 001.core-fixes (system)

**Stage:** 001.fixes · **Feature:** 001.core-fixes

Planning-time decisions for the core request, stream and settings fixes on the chat-completions OpenAI and llama-swap clients. Feature 001.core-fixes, delivered 2026-11-07. The wording notes on DEC-001-1, DEC-001-7 and DEC-001-9 were added at finalization (2026-11-08).

Module names: these entries were written when the chat-completions classes lived in `llm/openai.py` and `llm/llama_swap.py`. Feature 003.responses-chat moved them, as renamed copies, to `llm/openai_chat_completions.py` and `llm/llama_swap_chat_completions.py` (DEC-003-7), and the Lands in lines below name those modules. The Responses classes now under the original module names were built from the fixed classes (DEC-003-3) and carry their own copies: their tool loop follows the same rules per DEC-004-11; their settings, reply and stream handling are realized in the DEC-003 entries.

### DEC-001-1 — Early stream end raises unless a finish reason or a done frame arrived
- **Status:** accepted
- **Stage:** 001.fixes · **Feature:** 001.core-fixes · **Step:** 003
- **Date:** 2026-11-07 · **Decided by:** user
- **Question:** When does a chat-completions stream count as ended early (US-024.AC-2)?
- **Decision:** Both stream parsers track two completion signals: a non-null `finish_reason` on any choice and the `data: [DONE]` frame. When the reader is exhausted and neither was seen, the parser raises `LLMError` stating that the stream ended before the reply was complete. Either signal alone is enough. A transfer cut mid-body (a payload error, disconnect or timeout raised while reading) also raises `LLMError`, mapped in the stream reader (DEC-001-7). Together with DEC-001-9 this supersedes DEC-000-13.
- **Reason:** Some OpenAI-compatible servers omit `[DONE]` and some omit `finish_reason`; accepting either keeps them working while a stream with no completion signal at all is reported instead of returned as partial text.
- **Rejected:** Require `[DONE]` (breaks servers that omit it). Require `finish_reason` (same problem for servers that omit it).
- **Note:** 2026-11-08, at finalization (from the coder's observation, step 003) — exact wording as shipped: the early end raises `LLMError` with message `The stream ended before the reply was complete` and no description. `[DONE]` is matched after stripping surrounding whitespace from the payload. A read failure in the stream reader reuses the transport shape of DEC-001-7 (`Request to <url> failed: <kind>`), with the response's URL as `<url>`. The strings live in code only.
- **Lands in:** `llm/llm_client.py` (`_stream_openai_chat_response`, `_stream_openai_tools_response`, `_iter_sse_data`)
- **Cites:** docs/architecture/interfaces.md § Exposed: error contract (in-stream error piece or early end); US-024.AC-2; DEC-000-13

### DEC-001-2 — chat_json uses the response format setting when the app set one
- **Status:** accepted
- **Stage:** 001.fixes · **Feature:** 001.core-fixes · **Step:** 004, 005
- **Date:** 2026-11-07 · **Decided by:** user
- **Question:** `response_format` becomes a sent setting (DEC-001-14); which wins in `chat_json`, the setting or the built-in JSON-object request?
- **Decision:** On OpenAI and llama-swap, when the merged settings carry `response_format`, `chat_json` sends that value; otherwise it sends `{"type": "json_object"}`. The parse check stays as in DEC-000-37. Ollama is unchanged (`"format": "json"`). Supersedes DEC-000-36.
- **Reason:** It lets an app request a `json_schema` answer through `chat_json`.
- **Rejected:** `chat_json` always sends the JSON-object format (the app's schema format would be silently replaced).
- **Lands in:** `chat_json` in `llm/openai_chat_completions.py`, `llm/llama_swap_chat_completions.py` (Responses copies: see the module-name note above)
- **Cites:** docs/architecture/interfaces.md § Exposed: capability matrix (`chat_json` request row); DEC-000-36; DEC-001-14

### DEC-001-6 — The OpenAI client refuses a missing credential and never reads the environment
- **Status:** accepted
- **Stage:** 001.fixes · **Feature:** 001.core-fixes · **Step:** 004
- **Date:** 2026-11-07 · **Decided by:** planner
- **Question:** Where does the OpenAI client get its credential, and how is a missing one refused?
- **Decision:** The constructor uses its `bearer_token` argument only; the environment reads (`OPEN_AI_KEY`, `OPENAI_API_KEY`) and the `os` import are removed. `None` or an empty string raises `ValueError` in the constructor, before any session or request, with a message telling the developer to pass a credential (naming the `bearer_token` argument) that mentions no environment variable and contains no credential value. The constructor signature is unchanged. Live tests read their own environment variable and pass it as `bearer_token`. Supersedes DEC-000-2.
- **Reason:** The architecture fixes `ValueError` at creation for a missing OpenAI credential; naming the argument tells the developer what to do without suggesting the library reads an environment variable.
- **Rejected:** `LLMError` for the refusal (the architecture's error contract names `ValueError`). Making `bearer_token` a required positional argument (breaks the shared constructor shape).
- **Lands in:** `llm/openai_chat_completions.py` (constructor, class docstring; Responses copy: see the module-name note above); `tests/integrations/`
- **Cites:** docs/architecture/interfaces.md § Exposed: factory, § Exposed: error contract (missing OpenAI credential); US-003.AC-2, US-003.AC-3, US-003.AC-4; DEC-000-2

### DEC-001-7 — Transport failures map to LLMError carrying the address
- **Status:** accepted
- **Stage:** 001.fixes · **Feature:** 001.core-fixes · **Step:** 002, 003
- **Date:** 2026-11-07 · **Decided by:** planner
- **Question:** Which transport failures become the library error, where, and what does the error text say?
- **Decision:** `aiohttp.ClientError` other than the status error, and `TimeoutError` (`asyncio.TimeoutError`), are caught in three places: around the request and body read in `_request`; around opening the request in `_stream_post` (DEC-001-8); and around reading in `_iter_sse_data`. Each raises `LLMError` chained from the original. The message names the request address and the failure kind (connection failure, timeout, interrupted transfer) and the description is the original exception's text; neither is built from request headers. The text never contains the phrase "status <n>", so the deprecated Ollama embed fallback (DEC-000-42) still triggers only on a real 404. In the reader the address is the response's URL. This reaches the Ollama client through `_request` unchanged in shape. Non-JSON 2xx replies are not mapped here (feature 002). Supersedes DEC-000-12.
- **Reason:** One mapping per read point covers every operation on every backend, keeps receiver failures out of the catch (they run in the parsers), and keeps the Ollama fallback's text match correct.
- **Rejected:** Mapping mid-stream failures in the streamed-request helper's block exit (it would also convert a receiver's own exceptions of those types). A shared helper building the message (no frozen symbol existed for it; coder, step 002).
- **Note:** 2026-11-08, at finalization (from the coder's observation, step 002) — exact wording as shipped: message `Request to <url> failed: <kind>`, where kind is `timeout`, `interrupted transfer` (server disconnect or payload error: `ServerDisconnectedError`, `ClientPayloadError`) or `connection failure` (any other client error); the timeout is tested first. The description is the original exception's text, or its type name when that text is empty, with the bearer token redacted if it ever appears. The strings live in code only.
- **Lands in:** `llm/llm_client.py` (`_request`, `_stream_post`, `_iter_sse_data`)
- **Cites:** docs/architecture/interfaces.md § Exposed: error contract (transport failure); US-011.AC-3, US-011.AC-4; DEC-000-12; DEC-000-42

### DEC-001-8 — Streamed requests open through one base helper
- **Status:** accepted
- **Stage:** 001.fixes · **Feature:** 001.core-fixes · **Step:** 002, 004, 005
- **Date:** 2026-11-07 · **Decided by:** planner
- **Question:** How do the four streamed chat-completions sites report a non-2xx reply with the server's reply (DEC-arch-5)?
- **Decision:** A new `LLMClient._stream_post(path, payload)` async context manager owns opening a streamed POST: session, bearer header only when a token is set, `ClientTimeout(total=self.timeout)`, the non-2xx check, which reads the body and raises `LLMError(f"Request to {url} failed with status {status}", description=<body>)` (the DEC-000-11 format), and the transport mapping of DEC-001-7. On 2xx it yields the open response and releases it when the block exits; it does not catch exceptions raised in the block. The streamed `chat` branch and `_tools_stream_request` in the two chat-completions modules use it; `_tools_stream_request` stays the test seam for a streamed tool round. This delivers the chat-completions half of DEC-arch-5. The Responses classes (feature 003) may reuse it. Being protocol-neutral HTTP plumbing on the base, it does not conflict with DEC-arch-2. DEC-000-35 still holds for everything above the request.
- **Reason:** One helper fixes four identical sites at once, carries the credential rule in one place, and gives later protocol classes the same behaviour without copying it.
- **Rejected:** Per-class inline fixes in each of the four sites (four copies of the body read and the mapping, easy to drift).
- **Lands in:** `llm/llm_client.py` (`_stream_post`); `llm/openai_chat_completions.py`, `llm/llama_swap_chat_completions.py` (`chat`, `_tools_stream_request`)
- **Cites:** docs/architecture/interfaces.md § Exposed: error contract (streamed non-2xx); docs/architecture/subsystems.md § Base client (`LLMClient`); DEC-arch-5; DEC-000-10; DEC-000-11

### DEC-001-9 — In-stream error frames raise LLMError and malformed frames are skipped
- **Status:** accepted
- **Stage:** 001.fixes · **Feature:** 001.core-fixes · **Step:** 003
- **Date:** 2026-11-07 · **Decided by:** planner
- **Question:** What do the two chat-completions parsers do with an error frame and with frames they cannot read?
- **Decision:** A decoded JSON object with a truthy `error` key raises `LLMError` at once, in both parsers, whether or not it also has `choices`. The message says the server reported an error in the stream; the description is the server's reason: `error.message` when the error is an object with a string message, otherwise the error value as JSON text. Frames that are not JSON, JSON values that are not objects, and objects without `choices` and without `error` (e.g. usage frames) are skipped without error. A stream left with only skipped frames still fails the end check (DEC-001-1). Together with DEC-001-1 this supersedes DEC-000-13.
- **Reason:** The error frame carries the server's reason, and the cross-feature rule wants it reported. Skipping other unreadable frames keeps servers that send extension or keep-alive data working, and truncation is caught by the end check anyway.
- **Rejected:** Raising on any non-JSON or non-object frame (fails on harmless server extensions). A module-level message constant (no frozen symbol existed for it; coder, step 003).
- **Note:** 2026-11-08, at finalization (from the coder's observation, step 003) — exact wording as shipped: message `The server reported an error in the stream`; the description is the error's `message` when it is a string, otherwise the error serialised as JSON with non-ASCII characters kept (`ensure_ascii=False`). The strings live in code only.
- **Lands in:** `llm/llm_client.py` (`_stream_openai_chat_response`, `_stream_openai_tools_response`)
- **Cites:** docs/architecture/interfaces.md § Exposed: error contract, § Consumed: backend APIs (SSE stream format); US-024.AC-1; DEC-000-13

### DEC-001-10 — Stream reader decodes incrementally and follows SSE line and event rules
- **Status:** accepted
- **Stage:** 001.fixes · **Feature:** 001.core-fixes · **Step:** 003
- **Date:** 2026-11-07 · **Decided by:** planner
- **Question:** How is the raw byte stream cut into event payloads (US-036)?
- **Decision:** `_iter_sse_data` reads `response.content.iter_chunked(...)` and decodes with one incremental UTF-8 decoder for the whole stream (`errors="replace"`), so a character split between reads is kept and invalid bytes become visible rather than vanishing. Lines end at LF, CRLF or bare CR; a CR at the end of one read followed by LF at the start of the next is one terminator. Per SSE: a line starting with `:` is a comment; `data` field values (one leading space removed) accumulate and are joined with `\n`; a blank line dispatches the event if it has data; `event`, `id`, `retry` and unknown fields are ignored on chat completions. At end of stream a pending event with data is dispatched. `[DONE]` is yielded as a payload for the parsers. Read failures map per DEC-001-7. Supersedes DEC-000-34.
- **Reason:** Implements the stream rules the architecture already states, and keeps the reader shared by both protocols' data-only parsing.
- **Rejected:** Per-chunk decoding with `errors="ignore"` (loses split characters silently). Yielding each `data:` line separately (splits one event's payload).
- **Lands in:** `llm/llm_client.py` (`_iter_sse_data`)
- **Cites:** docs/architecture/interfaces.md § Consumed: backend APIs (SSE stream format); US-036.AC-1, US-036.AC-2, US-036.AC-3; DEC-000-34

### DEC-001-11 — A delta with reasoning and content delivers both
- **Status:** accepted
- **Stage:** 001.fixes · **Feature:** 001.core-fixes · **Step:** 003
- **Date:** 2026-11-07 · **Decided by:** planner
- **Question:** In the plain parser, what reaches the receiver when one delta carries both `reasoning_content` and `content`?
- **Decision:** Two pieces, in order: the reasoning (prefixed with `<think>` if it opens the block), then the content (prefixed with `</think>`, which closes the block). Both are added to the returned text, so it still equals what the receiver got. Only `reasoning_content` is read as reasoning (DEC-000-20); no other field name is added. The tools parser already handles both and is unchanged. Supersedes DEC-000-21.
- **Reason:** Keeps one piece per kind of text and the existing marker rules, so receivers that show or hide reasoning by marker keep working.
- **Rejected:** One combined piece holding reasoning, closing marker and content (mixes both kinds in one receiver call).
- **Lands in:** `llm/llm_client.py` (`_stream_openai_chat_response`)
- **Cites:** docs/architecture/subsystems.md § Streaming and reasoning; US-026.AC-4, US-026.AC-5; DEC-000-20; DEC-000-21

### DEC-001-12 — Null reply content becomes empty text where it is extracted
- **Status:** accepted
- **Stage:** 001.fixes · **Feature:** 001.core-fixes · **Step:** 004, 005
- **Date:** 2026-11-07 · **Decided by:** planner
- **Question:** Where is a null `content` in a non-streamed reply turned into empty text, and does the tracer change?
- **Decision:** On OpenAI and llama-swap, a null content becomes `""` at each extraction point, before tracing and before returning: `chat` (and so `generate`), `chat_json`, the final answer of `chat_with_tools`, and the content of the assistant tool-call turn appended to the round's conversation. `llm/trace.py` is not changed: with coercion at the source it never receives `None` from these paths. Malformed replies (missing choice or message) still surface as generic errors (accepted). The deprecated Ollama client is not changed. Supersedes DEC-000-9.
- **Reason:** Fixing the value at the source gives the app one type and keeps the tracer fix (feature 002's area) out of this feature.
- **Rejected:** Making the tracer accept `None` (the app would still get `None`).
- **Lands in:** `llm/openai_chat_completions.py`, `llm/llama_swap_chat_completions.py` (`chat`, `chat_json`, `chat_with_tools`; Responses copies: see the module-name note above)
- **Cites:** docs/architecture/interfaces.md § Exposed: error contract (null content); US-009.AC-1, US-009.AC-3; DEC-000-9

### DEC-001-13 — OpenAI and llama-swap tables carry no built-in values
- **Status:** accepted
- **Stage:** 001.fixes · **Feature:** 001.core-fixes · **Step:** 004, 005
- **Date:** 2026-11-07 · **Decided by:** planner
- **Question:** How does "only settings the app set are sent" fit the three-layer merge and the "nothing removes the setting" rule?
- **Decision:** Every value in `_OPENAI_SUPPORTED_PARAMS` and the llama-swap table is `None`, so the lowest layer contributes no value and the existing None-strip leaves only keys the app set. `_merge_options_base` is unchanged: aliases, unknown-key drop, call over client default, and `None` at a higher layer removing a key all stay as in DEC-000-5. The OpenAI thinking post-processing adds nothing when the switch is unset (DEC-000-19). Ollama's table and its built-in values are unchanged because the client is deprecated and observation-only. Supersedes DEC-000-6.
- **Reason:** A table-level change fixes both OpenAI-family clients without touching the shared algorithm, so Ollama's requests stay exactly as they are.
- **Rejected:** Splitting "supported names" from "built-in values" in the base merge (changes Ollama's requests or forces an Ollama edit).
- **Lands in:** `llm/openai_chat_completions.py`, `llm/llama_swap_chat_completions.py` (supported tables; Responses tables: DEC-003-9)
- **Cites:** docs/architecture/subsystems.md § Options layer; docs/architecture/data-model.md § Settings; US-018.AC-1; DEC-000-5; DEC-000-6

### DEC-001-14 — Offered settings keys join the OpenAI and llama-swap tables
- **Status:** accepted
- **Stage:** 001.fixes · **Feature:** 001.core-fixes · **Step:** 001, 004, 005
- **Date:** 2026-11-07 · **Decided by:** planner
- **Question:** How do `stop`, `logit_bias`, `user` and `response_format`, declared in `OpenAIOptions`, reach the server?
- **Decision:** They are added (value `None`) to the OpenAI and llama-swap supported tables, so they are merged like any other key and spread top-level into every chat-style request (`chat`, `generate`, `chat_json`, `chat_with_tools`). No alias is added. `OpenAIOptions.response_format` is hinted as a mapping to any value so a `json_schema` format type-checks. The Ollama keys declared in `OllamaOptions` but absent from its table stay dropped (deprecated, not extended). Supersedes DEC-000-7.
- **Reason:** The keys are already part of the public settings shape; adding them to the tables is the merge's own mechanism.
- **Lands in:** `llm/openai_chat_completions.py`, `llm/llama_swap_chat_completions.py` (supported tables; Responses tables: DEC-003-9); `llm/options.py`
- **Cites:** docs/architecture/data-model.md § Settings; US-019.AC-1; DEC-000-7; DEC-000-17

### DEC-001-15 — In a tool chat the response format parameter wins over the setting
- **Status:** accepted
- **Stage:** 001.fixes · **Feature:** 001.core-fixes · **Step:** 004, 005
- **Date:** 2026-11-07 · **Decided by:** planner
- **Question:** `chat_with_tools` has its own `response_format` parameter and now also a `response_format` setting; which is sent?
- **Decision:** A truthy parameter is sent and replaces the setting; without it the setting (if set) is sent. This is the existing payload order (parameter applied after the settings are spread). It applies on every round (DEC-000-30).
- **Reason:** The explicit argument of one call is the most specific intent, and the order already exists in both clients.
- **Rejected:** Setting wins (an explicit argument would be ignored).
- **Lands in:** `chat_with_tools` in `llm/openai_chat_completions.py`, `llm/llama_swap_chat_completions.py` (Responses copies: DEC-004-10)
- **Cites:** docs/architecture/interfaces.md § Tool loop contract; DEC-000-30; DEC-001-14

### DEC-001-16 — The embedding end-user id keeps its direct read
- **Status:** accepted
- **Stage:** 001.fixes · **Feature:** 001.core-fixes · **Step:** 004, 005
- **Date:** 2026-11-07 · **Decided by:** planner
- **Question:** `user` is now a merged setting (DEC-001-14); does `embed_batch` switch to the merge?
- **Decision:** No. `embed_batch` keeps reading `user` directly from the call's options, else the client defaults, and sends it only when truthy (DEC-000-39). It still does not call the settings merge, so no generation setting reaches an embedding request.
- **Reason:** The current behaviour is accepted and meets US-041.AC-3/AC-4; going through the merge would let a per-call `None` clear the client's id, a change no story asks for.
- **Rejected:** Reading `user` from the merged settings (changes the accepted clearing rule).
- **Lands in:** `llm/openai_chat_completions.py`, `llm/llama_swap_chat_completions.py` (`embed_batch`, unchanged; Responses copies: see the module-name note above)
- **Cites:** docs/architecture/data-model.md § Settings; US-041.AC-3, US-041.AC-4; DEC-000-39

# Decisions — 005.responses-live-tests (system)

**Stage:** — (not roadmapped) · **Feature:** 005.responses-live-tests

Planning-time decisions for the extra live tests of the Responses protocol (`OpenAIAPIClient`, `LlamaSwapAPIClient`) against real OpenAI and llama-swap servers. These tests cover multi-turn history, the system instruction, non-English streaming, streamed generate, token caps, ignored settings, answer formats, sampling and effort settings, credential and transport failures, concurrency and scope reuse, embeddings and model records, and extra tool conversations. The feature is test-only. The strategy it extends is DEC-arch-12. Servers, models and variables build on DEC-003-15. 004's own live tests (DEC-004-13) are not repeated.

### DEC-005-1 — Feature 005 changes no library code; live failures are findings
- **Status:** accepted — amended by DEC-005-16 (2026-11-08)
- **Stage:** — · **Feature:** 005.responses-live-tests · **Step:** 001, 002, 003, 004
- **Date:** 2026-11-08 · **Decided by:** planner
- **Question:** What happens when a new live test fails because the library does not meet the spec, and how does the test-writing / code-writing pipeline run when there is no source change?
- **Decision:** Every step has no Source files. No library file, and no existing test file, is edited.
  - **Live failure.** A new live test that fails because the library misbehaves is a finding. The verifier reports it with Fault SPEC, meaning out of scope for 005, not CODE. The orchestrator records it as an `[product]` / `[decision]` observation in `outcome.md` and routes it to `/bug-fixer`. It is never fixed inside 005, and the test is not weakened to pass. A failure caused by the test itself is Fault TEST as usual. A server that cannot be reached is reported as requires-live-run.
  - **Pipeline.** The skeleton freezes no library signature. It records "none: test-only" under `## Skeleton`. The shared helper module is test code, written by the test-coder. The red gate checks that the new tests are collected and that every `[test]` DoD item is covered. These tests are not expected to fail against the stubs, because there are none. The coder has nothing to implement. The verify run is the live run.
- **Reason:** The user asked for coverage of the delivered Responses implementation, not for changes to it. Keeping fixes out of 005 keeps every fix behind its own plan and its own tests.
- **Rejected:** Fixing a defect found live in the same step (that would add source scope to a test-only feature, without a plan or unit tests). Marking a known-at-risk spec check as an expected failure up front, as for the token-cap case on llama-swap (that would hide whether the spec is met; only DEC-005-9's environment limit is marked).
- **Amended:** 2026-11-08, planner — the rule also covers step 005. A cut check of steps 002 / 005 that fails before the library steps it depends on are done is not a finding; that run is not started (DEC-005-16).
- **Lands in:** `tests/integrations/AGENTS.md` § Conventions; `tests/integrations/test_responses_*.py` (no file under `llm/` changed)
- **Cites:** DEC-arch-12; the plans-layer contract (`AGENTS.md` of the plans folder) § Pipeline and ownership

### DEC-005-2 — New live files share one helper module; existing files are not migrated
- **Status:** accepted
- **Stage:** — · **Feature:** 005.responses-live-tests · **Step:** 001
- **Date:** 2026-11-08 · **Decided by:** planner
- **Question:** Where do the server, model and credential readers, the client builder, the piece recorder and the reasoning-marker checks live for the new live files, given that every existing live file duplicates them module-locally?
- **Decision:** In one new importable module, `tests/integrations/live_support.py`, whose module and function docstrings list its contents. It is imported as `tests.integrations.live_support` only by the files feature 005 adds, and it imports nothing from other test files. Existing live files keep their module-local helpers. There is no `conftest.py`, no fixture plugin and no pytest marker, and the new tests run in the default `uv run pytest` run. Test-specific helpers (prompts, tool callables, script checks) stay module-local in the file that uses them.
- **Reason:** Four new files need the same readers and checks. A single module keeps the environment rules in one place. Not touching existing files keeps the feature's scope to new coverage.
- **Rejected:** A `conftest.py` (implicit fixtures would also reach the existing files and the unit suite). Migrating the existing files (outside the user's request). A custom marker (not registered; pytest would warn, and live tests stay in the default run).

### DEC-005-4 — llama-swap tests turn thinking off; the OpenAI plain model gets no thinking setting
- **Status:** accepted
- **Stage:** — · **Feature:** 005.responses-live-tests · **Step:** 001, 002, 003, 004
- **Date:** 2026-11-08 · **Decided by:** planner
- **Question:** With which thinking setting do the new tests run? The llama-swap default model reasons when it gets no reasoning setting (DEC-003-2), and `gpt-4o-mini` refuses any effort (DEC-003-1).
- **Decision:**
  - **llama-swap.** The helper's builder gives llama-swap clients the client default `enable_thinking: false`, which is sent as effort `none`. A test may override it.
  - **OpenAI.** OpenAI clients get no thinking setting by default. The only OpenAI reasoning setting in 005 is the explicit `reasoning_effort: "medium"` on `OPENAI_REASONING_MODEL` (step 002).
  - **Defensive checks.** Checks that read answer text still go through the helper's answer-text extraction, and streamed checks still run the well-formed-block check, so that a reasoning block that does appear never breaks a structural check.
- **Reason:** Thinking off keeps llama-swap runs short and the replies answer-only. Thinking on/off itself is already covered live by the 003 protocol tests. Sending thinking off to `gpt-4o-mini` would be refused.
- **Rejected:** Leaving llama-swap at the server default (long reasoning on every call, and a token cap is spent inside reasoning). Turning thinking off on OpenAI too (refused by `gpt-4o-mini`).

### DEC-005-5 — One test function per backend; skip only for a missing OpenAI key
- **Status:** accepted
- **Stage:** — · **Feature:** 005.responses-live-tests · **Step:** 001, 002, 003, 004
- **Date:** 2026-11-08 · **Decided by:** planner
- **Question:** How are the backend-symmetric checks written and named, and when may a test skip?
- **Decision:**
  - **Naming and shape.** Each check is one `async def test_<backend>_<behaviour>__DoD<n>` per backend (`openai`, `llamaswap`) with `@pytest.mark.asyncio`. Shared bodies are module-local helpers, not backend parametrization. Streamed and non-streamed variants may share a body through a `stream` parameter (ids `streamed` / `not_streamed`). Every client is used inside `async with client:`.
  - **Skips.** OpenAI tests skip when the key chain is empty. llama-swap tests never skip. The bad-credential and unreachable-server tests (step 003) need no real key and never skip.
  - **Restrictions.** No test writes `os.environ`. Warnings are counted inside `warnings.catch_warnings(record=True)` with `simplefilter("always")`.
- **Reason:** These follow the folder conventions (backend token first in the name, async with, warning counting). The failure tests need no paid key, so they always run.
- **Rejected:** Backend parametrization of one test function (it breaks the `test_<backend>_` naming that the folder's tests use).
- **Lands in:** `tests/integrations/test_responses_*.py`
- **Cites:** tests/AGENTS.md § Conventions; tests/integrations/AGENTS.md § Conventions; DEC-003-6

### DEC-005-6 — Assertions are structural; two content checks are allowed
- **Status:** accepted — amended by DEC-arch-13 (2026-11-08)
- **Stage:** — · **Feature:** 005.responses-live-tests · **Step:** 001, 002
- **Date:** 2026-11-08 · **Decided by:** planner
- **Question:** What may the new live tests assert about model output?
- **Decision:** Only structural facts:
  - the type;
  - non-empty text;
  - JSON validity and required keys;
  - streamed return equal to the joined receiver pieces;
  - no `<think>` / `</think>` in a non-streamed return;
  - well-formed reasoning blocks in receiver output;
  - error type and error text properties;
  - warning counts.

  Two content checks are allowed:
  - **Multi-turn history.** The reply contains the neutral token that only the earlier assistant turn holds. The match ignores case. The token is a made-up code (e.g. `KQ7-4471`) that cannot be guessed.
  - **Token cap.** On a capped reply the call ends with `LLMError`. On OpenAI the error's description mentions `max_output_tokens`. On llama-swap the description is only required to be non-empty, because what llama.cpp reports is not documented.

  A well-formed reasoning block (the definition feature 003's and 004's live tests also use) is read strictly: markers balanced, every block closed, and answer text only after the last block. Output with no markers passes.
- **Reason:** Live models vary. A token placed only in the earlier assistant turn is the one way to prove the history reached the model. OpenAI documents the incomplete reason, llama.cpp does not.
- **Rejected:** Exact-text assertions. Requiring `max_output_tokens` on llama-swap (undocumented on llama.cpp).
- **Amended:** 2026-11-08, user — the "Token cap" content check: a reply cut at the app's own cap now returns non-empty text on both backends, with no error (DEC-arch-13); the `LLMError` and description expectations, and the Rejected line about `max_output_tokens` on llama-swap, no longer apply.
- **Lands in:** `tests/integrations/live_support.py` (reasoning-block and marker checks); `tests/integrations/test_responses_conversation.py`; `tests/integrations/test_responses_settings.py`
- **Cites:** tests/integrations/AGENTS.md § Conventions; DEC-003-12; DEC-003-13; US-006.AC-1; US-024.AC-2; US-060.AC-1

### DEC-005-7 — Structural checks for system instruction, scripts, streaming and embeddings
- **Status:** accepted
- **Stage:** — · **Feature:** 005.responses-live-tests · **Step:** 001, 003
- **Date:** 2026-11-08 · **Decided by:** planner
- **Question:** How are "the system instruction is followed", "non-English text arrives complete", "pieces arrive as produced" and "vectors come back in text order" checked without exact text?
- **Decision:**
  - **System instruction.** The instruction tells the model to answer only in uppercase letters, and the prompt asks for a short English answer. The answer text holds at least one letter, and every cased letter in it is uppercase.
  - **Non-English streaming.** The return equals the joined pieces. The return holds at least one Cyrillic letter (U+0400–U+04FF) and at least one Japanese character (hiragana U+3040–U+309F, katakana U+30A0–U+30FF or CJK ideograph U+4E00–U+9FFF). No piece and not the return holds U+FFFD. The prompt is the multilingual sea prompt already used by the live suite.
  - **Streamed generate.** The receiver gets at least two pieces, and the return equals their join. The prompt asks for three sentences.
  - **Embedding order.** The batch is three unrelated short texts. The batch gives three vectors of equal non-zero length. Each text is also embedded alone, and each batch vector has its highest cosine similarity with the single vector of the same text.
- **Reason:** Each check is a property any correct reply has, whatever the wording. The similarity check proves order without knowing vector values.
- **Rejected:** Comparing batch and single vectors for equality (servers do not promise bit-identical vectors). Requiring a fixed piece count (depends on the server's chunking).
- **Lands in:** `tests/integrations/test_responses_conversation.py`, `tests/integrations/test_responses_session.py`
- **Cites:** US-006.AC-2; US-012.AC-2; US-036.AC-1; US-036.AC-3; US-013.AC-1; US-013.AC-3; US-042.AC-2; US-042.AC-5

### DEC-005-8 — Inputs for the failure and ignored-setting tests
- **Status:** accepted — amended by DEC-arch-13 (2026-11-08)
- **Stage:** — · **Feature:** 005.responses-live-tests · **Step:** 002, 003
- **Date:** 2026-11-08 · **Decided by:** planner
- **Question:** Which values drive the token-cap, ignored-setting, bad-credential and unreachable-server tests?
- **Decision:**
  - **Token cap.** `max_tokens: 16` (the lowest output cap OpenAI accepts) with a prompt that asks for a long answer (e.g. a 500-word essay).
  - **Ignored setting.** `seed: 7` set per call on two calls of one client. A second client instance is then called once with the same setting.
  - **Bad credential.** The fixed key `sk-invalid-005-live-test-0000000000000000`, sent to OpenAI's address. The error must carry the refusal status `401` and a non-empty server reply as its description. That key must appear nowhere in the error's text, repr, message or description.
  - **Unreachable server.** The address `http://127.0.0.1:1/v1` (a closed local port), with a client time limit of 10 s. The OpenAI client gets the dummy key. The error text must contain `127.0.0.1:1`.
- **Reason:** 16 is OpenAI's minimum output cap, so the call is valid and is cut off at once. `seed` is a no-counterpart setting on both classes (DEC-003-9). The dummy key and the closed port need no secret and no remote server, so these tests always run. The short limit keeps a filtered port from stalling the run.
- **Rejected:** Using the real key with a corrupted suffix (risk of leaking key material into test output). A non-routable remote address (slow, and it depends on the network).
- **Amended:** 2026-11-08, user — the "Token cap" input is unchanged (`max_tokens: 16`, long-answer prompt), but the expected outcome changes: the cut reply is returned as non-empty text, not `LLMError` (DEC-arch-13).
- **Lands in:** `tests/integrations/test_responses_settings.py`, `tests/integrations/test_responses_errors.py`
- **Cites:** DEC-003-6; DEC-003-9; DEC-003-12; DEC-001-7; DEC-arch-5; US-024.AC-2; US-060.AC-1; US-060.AC-4; US-061.AC-1; US-061.AC-2; US-011.AC-3

### DEC-005-9 — The llama-swap json_schema checks are expected failures, not strict
- **Status:** accepted — amended 2026-11-08
- **Stage:** — · **Feature:** 005.responses-live-tests · **Step:** 002, 004
- **Date:** 2026-11-08 · **Decided by:** planner
- **Question:** How are the `json_schema` answer-format checks run on llama-swap? The 003 verify run saw llama.cpp's schema grammar fail there.
- **Decision:** The llama-swap variants of the `json_schema` checks (chat, chat_json, and the streamed tool conversation with a schema answer) carry `pytest.mark.xfail(strict=False, reason="llama.cpp json_schema grammar")`. A pass is reported as XPASS and is not an error. The OpenAI variants are plain assertions. No other check in 005 is marked as an expected failure.
- **Reason:** The failure is in the server environment, not in the library. A non-strict mark keeps the check running, so it shows when the server is fixed.
- **Rejected:** Skipping on llama-swap (the check would never run). Strict xfail (a fixed server would fail the run).
- **Amended:** 2026-11-08, at finalization (live-run evidence) — the llama-swap Responses `chat` and `chat_json` `json_schema` checks now XPASS, while the streamed tool conversation with a schema answer still xfails: the llama.cpp grammar limit depends on the path and the prompt rather than being total. The marks stay non-strict on all three. The same non-strict mark, citing this entry and the llama.cpp grammar limit, was added on 2026-11-08 to the llama-swap `json_schema` + tools live test of the chat-completions classes (outside feature 005's own files).
- **Lands in:** `tests/integrations/test_responses_settings.py`, `tests/integrations/test_responses_tools_extra.py`; `tests/integrations/test_llm_tools_response_format.py` (chat-completions case, 2026-11-08)

### DEC-005-10 — Concurrent calls and reuse after the usage scope
- **Status:** accepted
- **Stage:** — · **Feature:** 005.responses-live-tests · **Step:** 003
- **Date:** 2026-11-08 · **Decided by:** planner
- **Question:** What shape does the concurrency and scope-reuse test take?
- **Decision:** One client, inside one `async with`, runs four calls at once through `asyncio.gather`: two streamed chats, each with its own recorder, and two non-streamed (one `chat`, one `generate`). All four return non-empty text, and each streamed return equals its own recorder's join, so pieces are not mixed between calls. After the scope closes, the same client object is used in a new `async with` for one non-streamed chat, which returns non-empty text.
- **Reason:** Four calls of both kinds exercise the shared session without a heavy load on a single-model llama-swap. Per-recorder equality is the observable proof that per-call state is separate.
- **Rejected:** Larger fan-out (llama-swap serves one model and queues, so the run gets slow and shows nothing more).
- **Lands in:** `tests/integrations/test_responses_session.py`
- **Cites:** DEC-000-24; US-029.AC-1; US-004.AC-2

### DEC-005-11 — Extra live tool tests: tools, history and answer format
- **Status:** accepted
- **Stage:** — · **Feature:** 005.responses-live-tests · **Step:** 004
- **Date:** 2026-11-08 · **Decided by:** planner
- **Question:** What do the extra Responses tool tests run, beyond 004's own (DEC-004-13)?
- **Decision:**
  - **Tool.** One neutral tool, `fetch_record`, with one text argument `record_id`. It returns a value that cannot be guessed for each id and records every id it was called with.
  - **Two records.** The prompt asks for records `A` and `B` and an answer using both. The check is that the tool was called for both ids and the answer is non-empty. Whether both calls came in one round is the model's choice and is not asserted.
  - **History with tool turns.** The caller's history holds a user turn, then an assistant turn with empty content and one tool call (`id` `call_prev_c`, `fetch_record`, arguments `{"record_id": "C"}` as JSON text), then the tool-result turn (`tool_call_id` `call_prev_c`), then a user turn that asks about record C's value and to fetch record D. The check is that the call completes with a non-empty answer and that the caller's list is unchanged.
  - **Pydantic and async.** The tool definition is built by `pydantic_to_openai_tool` from a model with a `record_id: str` field, and the callable is a coroutine function.
  - **Schema answer.** A streamed tool conversation with `response_format` `json_schema` requires the keys `record_id` and `value`. The final answer parses as a JSON object holding both keys, and the returned answer is contained in what the receiver got.
  - **Settings.** `max_loops` stays at its default. Models per DEC-005-3, thinking per DEC-005-4.
  - **Dependency.** The step runs only once feature 004 is delivered.
- **Reason:** These cover several calls, caller-supplied tool turns (DEC-004-6), typed and async tools, and a schema answer on Responses, without repeating 004's single-call, two-round and json_object tests.
- **Rejected:** Asserting that both records came in one round (the model decides; that is not a library property).
- **Lands in:** `tests/integrations/test_responses_tools_extra.py`
- **Cites:** DEC-004-6; DEC-004-13; DEC-005-9; US-030.AC-1; US-030.AC-2; US-031.AC-1; US-023.AC-1; US-023.AC-2; US-037.AC-1; US-037.AC-4; US-057.AC-1

### DEC-005-12 — A reply cut at the app's limit: chat and generate checks on both backends
- **Status:** accepted
- **Stage:** — · **Feature:** 005.responses-live-tests · **Step:** 002, 005
- **Date:** 2026-11-08 · **Decided by:** planner
- **Question:** Which calls and variants check US-062.AC-1..AC-3 live, and what does each assert, now that a reply cut at the app's own token cap is returned as text (DEC-arch-13)?
- **Decision:**
  - **Calls.** With the cap and prompt of DEC-005-8 on both backends: `chat` non-streamed and streamed with a recorder; `generate` non-streamed and streamed with a recorder; and one variant where the cap is a client default (`default_options`) and the call options carry none, as non-streamed `chat`. The `context_length` alias is not checked live.
  - **Models.** OpenAI uses `OPENAI_MODEL`, a non-reasoning model. llama-swap runs thinking off (DEC-005-4). The reasoning model is not used for a cut check.
  - **Checks.** No `LLMError`. The answer text (helper extraction) is non-empty. Non-streamed: no reasoning marker. Streamed: the return equals the joined recorder pieces and the recorder output passes the well-formed-block check (DEC-005-6).
  - **No notice.** The call runs inside `warnings.catch_warnings(record=True)` with `simplefilter("always")`. No recorded warning has a category that is `UserWarning` or a subclass of it (this includes `LLMSettingIgnoredWarning`). Other categories (deprecation, resource, runtime warnings from third-party libraries) are not counted.
  - **Same checks in step 005.** The tool-conversation cut checks (DEC-005-13) use the same models, the same no-error and non-empty checks and the same notice filter.
- **Reason:** These are the operations US-062.AC-1 names, and the two ways the app can set the limit (DEC-arch-13). A non-reasoning model puts the 16 tokens into answer text; a reasoning model could spend them on hidden reasoning and return no text. The `UserWarning` family is where the library's own notices live (DEC-arch-6), so the filter finds a cut notice without being broken by unrelated library noise.
- **Rejected:** Asserting that the reply was in fact cut (a word or length bound): it is a model property; a 500-word essay under a 16-token cap cannot finish. Counting only `LLMSettingIgnoredWarning` (a new notice of another category would pass unseen). Counting every warning (third-party deprecation and resource warnings would break the test). Checking the alias live (unit-covered by feature 003 steps 006 / 007 DoD-2).
- **Lands in:** `tests/integrations/test_responses_settings.py`, `tests/integrations/test_responses_output_limit.py`
- **Cites:** DEC-arch-13; DEC-arch-6; DEC-003-17; DEC-003-19; DEC-005-6; DEC-005-8; US-062.AC-1; US-062.AC-2; US-062.AC-3; US-062.AC-4

### DEC-005-13 — A tool conversation whose final answer is cut: prompt and checks
- **Status:** accepted
- **Stage:** — · **Feature:** 005.responses-live-tests · **Step:** 005
- **Date:** 2026-11-08 · **Decided by:** planner
- **Question:** How is US-062.AC-4 (the final answer of a tool conversation cut at the app's limit is returned) checked live, given that whether the model calls a tool is the model's choice?
- **Decision:**
  - **Setup.** `chat_with_tools` with one neutral tool offered (one text argument; neutral name and value, written in the step's own file), the long-answer prompt of DEC-005-8, a system instruction saying that no tool is needed and the answer is plain prose, and the cap as a call option. `max_loops` stays at its default. Both backends, non-streamed and streamed with a recorder.
  - **Checks.** As DEC-005-12: no `LLMError`, non-empty answer text, no notice. Non-streamed: no reasoning marker. Streamed: the stripped return is contained in the recorder output, and the recorder output passes the well-formed-block check. Whether the tool ran is not asserted.
  - **Model calls the tool anyway.** A call that fits under the cap runs and the next round's answer is cut, which still meets US-062.AC-4. A call cut mid-arguments ends with `LLMError` by design (DEC-004-16 / DEC-004-17); the verifier treats such a failure as Fault TEST (prompt design), not a finding.
  - **Not forced live.** A cut inside a tool-call round, which must end with `LLMError`, is not provoked live. It is covered by the unit tests of feature 004 steps 005 / 006.
- **Reason:** The no-tool instruction makes the cut land in the answer round, which is the case the story names. Forcing a cut inside a call depends on how many tokens the model spends on the call, so it cannot be made reliable live.
- **Rejected:** Forcing a tool call and cutting its arguments live (non-deterministic). Asserting that the tool did not run (the model decides). Reusing step 004's tool helpers (DEC-005-2 keeps test helpers module-local, and step 004's file is done).
- **Lands in:** `tests/integrations/test_responses_output_limit.py`
- **Cites:** DEC-arch-13; DEC-004-16; DEC-004-17; DEC-005-2; DEC-005-12; US-062.AC-4; US-057.AC-1

### DEC-005-14 — A cut checked JSON answer ends with the invalid-JSON error, no expected failure
- **Status:** accepted
- **Stage:** — · **Feature:** 005.responses-live-tests · **Step:** 005
- **Date:** 2026-11-08 · **Decided by:** planner
- **Question:** How is US-062.AC-5 (a checked JSON answer cut at the app's limit fails like any invalid JSON answer) checked live, and does DEC-005-9's expected-failure mark apply?
- **Decision:** `chat_json` with an expected shape given (so the parse check runs, DEC-000-37), no `response_format` in the options (so the class asks for the plain JSON text format), the cap as a call option, and a prompt that asks for a long JSON answer (a list of many records) and names "JSON". Both backends. The check is that the call ends with `LLMError`; nothing else about the error is asserted. Neither variant carries an expected-failure mark: DEC-005-9 covers the `json_schema` grammar, which this check does not use. A cut answer that happens to parse is Fault TEST (prompt design), not a finding.
- **Reason:** The plain JSON format is grammar-free on OpenAI and a simple JSON grammar on llama.cpp, so the 16-token cut gives invalid JSON on both. ### DEC-005-16 — Cut tests run only after the library steps; the tool and JSON cuts get their own step
- **Status:** accepted

- **Date:** 2026-11-08 · **Decided by:** planner
- **Question:** Where do the new cut checks live, and when may their live verify run start, given that the OpenAI behaviour they check lands in pending steps of features 003 and 004?
- **Decision:**

Putting everything in step 002 (one file mixing settings checks with tool helpers, and a step that must also wait for feature 004). Marking the OpenAI variants as expected failures until the library lands (DEC-005-1 rejects marking spec checks).
